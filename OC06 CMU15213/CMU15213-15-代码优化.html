Slide 9–10

Goals of compiler optimization — Minimize number of instructions · Don't do calculations more than once · Don't do unnecessary calculations at all · Avoid slow instructions (multiplication, division) · Avoid waiting for memory · Keep everything in registers whenever possible · Access memory in cache-friendly patterns · Load data from memory early, and only once · Avoid branching · Don't make unnecessary decisions at all · Make it easier for the CPU to predict branch destinations · “Unroll” loops to spread cost of branches over more instructions

Limits to compiler optimization — Generally cannot improve algorithmic complexity · Only constant factors, but those can be worth 10x or more… · Must not cause any change in program behavior · Programmer may not care about “edge case” behavior, but compiler does not know that · Exception: language may declare some changes acceptable · Often only analyze one function at a time · Whole-program analysis (“LTO”) expensive but gaining popularity · Exception: inlining merges many functions into one · Tricky to anticipate run-time inputs · Profile-guided optimization can help with common case, but… · “Worst case” performance can be just as important as “normal” · Especially for code exposed to malicious input (e.g. network servers)

编译器优化的三个目标: ① 减少指令数: 不重复计算, 不做多余计算, 避开乘除这类慢指令; ② 少等内存: 尽量放寄存器, 访存模式对缓存友好, 早点读、只读一次; ③ 少分支: 去掉不必要的判断, 让分支容易预测, 展开循环以摊薄分支开销.

编译器的局限: 一般不能改进算法复杂度, 只能改进常数因子 (但常数因子也可能有 10 倍以上); 不能改变程序行为, 程序员不在乎的边界情况编译器也必须照顾 (除非语言规定可以不管, 例如有符号溢出是未定义行为); 通常一次只分析一个函数 (链接时优化 LTO 能做全程序分析但代价高; 内联则把多个函数合成一个); 难以预知运行时输入 (剖析引导优化 PGO 能照顾常见情况, 但对面对恶意输入的服务器, 最坏情况同样重要).

Slide 11

Two kinds of optimizations

  • Local optimizations work inside a single basic block · Constant folding, strength reduction, dead code elimination, (local) CSE, …
  • Global optimizations process the entire control flow graph of a function · Loop transformations, code motion, (global) CSE, …

两类优化. 基本块是一段中间没有跳入跳出的直线代码 (控制流图中的一个方框). 局部优化在单个基本块内进行: 常量折叠、强度削弱 (乘法换移位等)、死代码删除、局部公共子表达式消除. 全局优化处理整个函数的控制流图: 循环变换、代码外提、全局公共子表达式消除等.

常见优化
Examples of optimizations

Slide 13–15

Next several slides done live… https://godbolt.org/z/Es5s8qsvj · Go to Godbolt (the compiler explorer) to play around with C and the resulting assembly generated under different compiler optimizations (change the flag from –O3 to –Og, etc. to see more or less aggressive optimization).

Constant folding — Do arithmetic in the compiler: long mask = 0xFF << 8; → long mask = 0xFF00; · Any expression with constant inputs can be folded · Might even be able to remove library calls… size_t namelen = strlen("Harry Bovik"); → size_t namelen = 11;

Dead code elimination — Don't emit code that will never be executed: if (0) { puts("Kilroy was here"); } if (1) { puts("Only bozos on this bus"); } · Don't emit code whose result is overwritten: x = 23; x = 42; · These may look silly, but... · Can be produced by other optimizations · Assignments to x might be far apart

这几页课上用 Compiler Explorer (godbolt.org) 现场演示: 写 C 代码, 实时看不同优化级别 (-O3、-Og 等) 生成的汇编, 推荐自己试.

常量折叠: 输入全是常量的表达式在编译时算好, 0xFF << 8 直接变成 0xFF00; 甚至能把 strlen("Harry Bovik") 换成 11, 省掉库函数调用. 死代码删除: 永远不会执行的代码 (if (0) 的分支) 不生成, if (1) 的判断也去掉; 结果马上被覆盖的赋值 (x = 23 紧接着 x = 42) 删掉. 这些看似人不会写, 但常常是其他优化 (如内联、常量传播) 的产物, 或者两次赋值相隔很远.

Slide 16–17

Common subexpression elimination — Factor out repeated calculations, only do them once

norm[i] = v[i].x*v[i].x + v[i].y*v[i].y;
→
elt = &v[i];
x = elt->x;
y = elt->y;
norm[i] = x*x + y*y;

Code motion — Move calculations out of a loop · Only valid if every iteration would produce same result

long j;
for (j = 0; j < n; j++)
    a[n*i+j] = b[j];

long j;
int ni = n*i;
for (j = 0; j < n; j++)
    a[ni+j] = b[j];

公共子表达式消除 (CSE): 重复计算的部分只算一次. v[i] 的地址和 v[i].x、v[i].y 各算一次, 存在临时变量里.

代码外提 (code motion): 把每次迭代结果都相同的计算 (这里的 n*i) 移到循环外面, 只算一次.

幻灯片小错: 外提后的版本把 n*i 存进了 int ni, 而 n、i 在原代码中是 long (j 也是 long); 当 n*i 超过 int 范围时会截断, 改变程序行为, 编译器绝不会这样做. 应写 long ni = n*i; (教材中就是 long).

Slide 18–20

Inlining — Copy body of a function into its caller(s) · Can create opportunities for many other optimizations · Can make code much bigger and therefore slower (size; i-cache)

int pred(int x) {
    if (x == 0)
        return 0;
    else
        return x - 1;
}

int func(int y) {
    return pred(y)
         + pred(0)
         + pred(y+1);
}
int func(int y) {
    int tmp;
    if (y == 0) tmp = 0; else tmp = y - 1;
    if (0 == 0) tmp += 0; else tmp += 0 - 1;
    if (y+1 == 0) tmp += 0; else tmp += (y + 1) - 1;
    return tmp;
}

Always true · Does nothing · Can constant fold

int func(int y) {
    int tmp = 0;
    if (y != 0) tmp = y - 1;
    if (y != -1) tmp += y;
    return tmp;
}

内联: 把被调函数的函数体复制到调用处. 它本身省掉了调用开销, 更重要的是为其他优化创造机会; 代价是代码变大, 可能挤占指令缓存反而变慢.

例: func 三次调用 pred. 内联后得到三个 if; 第二个的条件 0 == 0 恒真, 而且只是 tmp += 0, 什么也不做, 整句删掉; 第三个的 (y + 1) − 1 常量折叠成 y, 条件 y + 1 == 0 改写为 y == −1. 最后只剩两个简单的判断. 不内联就看不出 pred(0) 恒为 0.

优化的障碍
Obstacles to optimization

Slide 22–23

Memory Aliasing

/* Sum rows of n X n matrix a and store in vector b. */
void sum_rows1(double *a, double *b, long n) {
    long i, j;
    for (i = 0; i < n; i++) {
        b[i] = 0;
        for (j = 0; j < n; j++)
            b[i] += a[i*n + j];
    }
}
    movq    $0, (%rsi)
    pxor    %xmm0, %xmm0
.L4:
    addsd   (%rdi), %xmm0
    movsd   %xmm0, (%rsi)
    addq    $8, %rdi
    cmpq    %rcx, %rdi
    jne     .L4

Code updates b[i] on every iteration · Why couldn't compiler optimize this away?

double A[9] =
  { 0,   1,   2,
    4,   8,  16,
   32,  64, 128};

double B[3] = A+3;

sum_rows1(A, B, 3);

Value of B: init: [4, 8, 16] · i = 0: [3, 8, 16] · i = 1: [3, 22, 16] · i = 2: [3, 22, 224] — (A becomes { 0, 1, 2, 3, 22, 224, 32, 64, 128}) · Must consider possibility that these updates will affect program behavior

内存别名: 两个指针可能指向同一块内存. sum_rows1 的内层循环每次都把累加结果写回 b[i] (汇编中循环里有 movsd %xmm0, (%rsi)), 而不是放在寄存器里最后写一次. 原因: 编译器无法排除 b 和 a 重叠的可能. 例: B 指向 A 的第 2 行 (B = A + 3), 那么写 b[i] 就改了 a 的元素, 后面的累加读到的是被改过的值. 逐步执行 (用 Python 模拟核对过): i = 0 时 b[0] = 0 + 1 + 2 = 3; i = 1 时 b[1] 先清零, 再加 A[3] (已是 3)、A[4] (就是 b[1] 本身)、A[5], 得 22; i = 2 得 224. 若把累加放在寄存器里, 结果会不同. 编译器必须保证这种情况下的行为不变, 只好每次都写内存.

Avoiding Aliasing Penalties

void sum_rows2(double *a, double *b, long n) {
    long i, j;
    for (i = 0; i < n; i++) {
        double val = 0;
        for (j = 0; j < n; j++)
            val += a[i*n + j];
        b[i] = val;
    }
}
    pxor    %xmm0, %xmm0
.L4:
    addsd   (%rdi), %xmm0
    addq    $8, %rdi
    cmpq    %rax, %rdi
    jne     .L4
    movsd   %xmm0, (%rsi)

Use a local variable for intermediate results · Use restrict keyword · Tells compiler that this is the “only” pointer to that memory location

避免别名的代价: 程序员用局部变量 val 累加, 循环结束后才写一次 b[i]; 局部变量的地址从未被取过, 不可能有别名, 编译器放心地把它放在寄存器里, 内层循环少了一次写内存. 另一个办法是给指针参数加 restrict 关键字 (C99), 向编译器保证这是访问那块内存的唯一指针. 注意: 若实际有重叠, 两种改法的结果会与 sum_rows1 不同, 这是程序员的责任.

Slide 25–26

Can't move function calls out of loops

void lower_quadratic(char *s) {
    size_t i;
    for (i = 0; i < strlen(s); i++)
        if (s[i] >= 'A' && s[i] <= 'Z')
            s[i] += 'a' - 'A';
}

void lower_still_quadratic(char *s) {
    size_t i, n = strlen(s);
    for (i = 0; i < n; i++)
        if (s[i] >= 'A' && s[i] <= 'Z') {
            s[i] += 'a' - 'A';
            n = strlen(s);
        }
}

void lower_linear(char *s) {
    size_t i, n = strlen(s);
    for (i = 0; i < n; i++)
        if (s[i] >= 'A' && s[i] <= 'Z')
            s[i] += 'a' - 'A';
}

Lots more examples of this kind of bug: accidentallyquadratic.tumblr.com · (strlen called every iteration / after each change)

函数调用阻碍代码外提. lower_quadratic 在循环条件里调用 strlen, 每次迭代都从头数一遍字符串, 总时间 O(n²). 编译器一般不敢把 strlen 移到循环外, 因为循环体修改了字符串, 它要证明这些修改不会改变长度 (这里其实不会, 但分析困难; strlen 在别的编译单元时更无从得知). lower_still_quadratic 只在修改后重新计算长度, 对全大写的字符串仍是平方级. lower_linear 只算一次, 线性时间. 网站 accidentallyquadratic 收集了大量真实软件中这类「不小心变成平方级」的 bug.

与机器相关的优化
Machine-dependent optimization

Slide 29–31

Modern CPU Design — Instruction Control (Fetch Control, Instruction Cache, Instruction Decode, Retirement Unit, Register File) → Operations → Execution (Functional Units: Branch, Arith, Arith, Arith, Load, Store; Data Cache) → Operation Results, Register Updates, Prediction OK?

Branches Are A Challenge — Instruction Control Unit must work well ahead of Execution Unit to generate enough operations to keep EU busy · (404663: mov $0x0,%eax · 404668: cmp (%rdi),%rsi · 40466b: jge 404685 — Need to know which way to branch …) · If the CPU has to wait for the result of the cmp before continuing to fetch instructions, may waste tens of cycles doing nothing!

Branch Prediction — Guess which way branch will go · Begin executing instructions at predicted position · But don't actually modify register or memory data

现代 CPU 分两大部分: 指令控制单元负责取指、译码, 把指令变成一串操作; 执行单元有多个功能单元 (分支、整数运算、读、写), 可以同时执行多个操作. 为了让执行单元一直有活干, 指令控制单元必须远远跑在前面.

分支是难题: 遇到 jge 时, 若要等前面的 cmp 算完才知道往哪走, 就会白白浪费几十个周期. 对策是分支预测: 猜一个方向, 先按猜测取指令并执行, 但暂不真正修改寄存器和内存 (结果先存在缓冲里, 确认猜对后才「退休」生效).

Slide 32–35

Branch Prediction Through Loop — Assume array length = 100 · (401029: mulsd (%rdx),%xmm0,%xmm0 · 40102d: add $0x8,%rdx · 401031: cmp %rax,%rdx · 401034: jne 401029) · i = 98: Predict Taken (OK) · i = 99: Predict Taken (Oops) · i = 100: Read invalid location, Executed · i = 101: Fetched

Branch Misprediction Invalidation — Invalidate · Branch Misprediction Recovery — 401034: jne 401029 (i = 99, Definitely not taken) · 401036: jmp 401040 · 401040: movsd %xmm0,(%r12) — Reload Pipeline · Performance Cost · Multiple clock cycles on modern processor · Can be a major performance limiter

Branch Prediction Numbers — A simple heuristic: · Backwards branches are often loops, so predict taken · Forwards branches are often ifs, so predict not taken · Fancier algorithms track behavior of each branch · Branch behavior often correlates · Other notes: · Subject of ongoing research · 2011 record (https://www.jilp.org/jwac-2/program/JWAC-2-program.htm): 34.1 mispredictions per 1000 instructions · Current research focuses on the remaining handful of “impossible to predict” branches (strongly data-dependent, no correlation with history) e.g. https://hps.ece.utexas.edu/pub/PruettPatt_BranchRunahead.pdf

循环中的预测: 数组长 100, 循环末尾的 jne 每次都预测「跳回去」, 前 99 次都对; 最后一次 (i = 99 之后) 预测错了, CPU 已经按猜测提前执行了 i = 100、101 的迭代 (甚至读了数组末尾之外的地址, 但结果并未生效). 发现猜错后, 把这些推测执行的指令全部作废, 从正确的地址 (循环后面) 重新取指. 代价是若干个时钟周期, 对分支多又难预测的代码是主要性能瓶颈.

预测方法: 简单启发式是向后跳的分支 (多为循环) 预测跳转、向前跳的分支 (多为 if) 预测不跳; 更好的算法记录每个分支的历史, 并利用分支之间的相关性. 现在大多数分支都能预测得很准, 研究集中在少数与数据强相关、无历史规律可循的「不可能预测」的分支上.

为分支预测优化: ① 减少分支数: 变换或展开循环; 用条件传送 (不总是好主意, 见第 4 讲). ② 让分支好预测: 例如把数据排序 (StackOverflow 上著名的问题: 对排序后的数组做同样的条件求和快好几倍); 避免间接跳转 (函数指针、C++ 虚函数), 它们的目标地址也要预测.

例子是转小写的循环: 第一版用条件跳转 ja 跳过非大写字母; 第二版先无条件算出 c + 32, 再用 cmova 在「不是大写字母」(c − 65 无符号大于 25) 时换回原字符, 然后无条件写回. 循环里只剩循环本身的分支, 但代价是每个字符都要写一次内存, 原来只有大写字母才写.

Slide 37–38

Loop Unrolling — Amortize cost of loop condition by duplicating body · Creates opportunities for CSE, code motion, scheduling · Prepares code for vectorization · Can hurt performance by increasing code size

for (size_t i = 0; i < nelts; i++) {
    A[i] = B[i]*k + C[i];
}

for (size_t i = 0; i < nelts - 4; i += 4) {
    A[i  ] = B[i  ]*k + C[i  ];
    A[i+1] = B[i+1]*k + C[i+1];
    A[i+2] = B[i+2]*k + C[i+2];
    A[i+3] = B[i+3]*k + C[i+3];
}

Scheduling — Rearrange instructions to make it easier for the CPU to keep all functional units busy · For instance, move all the loads to the top of an unrolled loop · Now maybe it's more obvious why we need lots of registers

for (size_t i = 0; i < nelts - 4; i += 4) {
    B0 = B[i]; B1 = B[i+1]; B2 = B[i+2]; B3 = B[i+3];
    C0 = C[i]; C1 = C[i+1]; C2 = C[i+2]; C3 = B[i+3];
    A[i  ] = B0*k + C0;
    A[i+1] = B1*k + C1;
    A[i+2] = B2*k + C2;
    A[i+3] = B3*k + C3;
}

When would this change be incorrect?

循环展开: 把循环体复制几份, 每次迭代处理几个元素, 循环判断和跳转的开销被摊薄; 还为公共子表达式消除、外提、指令调度和向量化创造机会; 但代码变大, 可能伤害性能.

指令调度: 重排指令, 让 CPU 的各功能单元都忙起来, 例如把展开后循环里的所有读操作都提到最前面. 这需要很多寄存器来暂存.

回答「什么时候这种改动会出错»: ① 展开版的循环条件 i < nelts − 4 本身就有问题: nelts 是 size_t, 小于 4 时 nelts − 4 绕回成一个极大的数, 循环越界; 即使 nelts ≥ 4, 也漏掉了最后 1 到 4 个元素, 需要一个收尾循环处理剩余元素 (条件应写成 i + 3 < nelts). ② 调度版把读提前到写之前, 若 A 与 B 或 C 有重叠 (别名), 例如 A[i] 就是 B[i+1], 原版中 B[i+1] 应读到刚写入的新值, 调度版读到的却是旧值, 结果不同.

幻灯片错误: 调度版中 C3 = B[i+3]; 应为 C3 = C[i+3];, 否则第 4 个元素算成 B[i+3]·k + B[i+3].

Basic Optimizations

void combine4(vec_ptr v, data_t *dest)
{
    long i;
    long length = vec_length(v);
    data_t *d = get_vec_start(v);
    data_t t = IDENT;
    for (i = 0; i < length; i++)
        t = t OP d[i];
    *dest = t;
}

Move vec_length out of loop · Avoid bounds check on each cycle · Accumulate in temporary

Effect of Basic Optimizations — Combine4: Integer Add 1.27 · Integer Mult 3.01 · Double FP Add 3.01 · Double FP Mult 5.01

combine4 做了三件事: 把 vec_length 移出循环 (代码外提); 直接拿数据数组指针, 免去每次的边界检查; 用局部变量 t 累加, 最后写一次 *dest (消除别名带来的内存读写). CPE 降到 1.27 (整数加)、3.01 (整数乘、浮点加)、5.01 (浮点乘). 后三个数恰好等于对应运算的延迟 (乘法 3 周期、浮点加 3 周期、浮点乘 5 周期): 每次运算都要等上一次的结果, 循环被这条数据依赖链卡住了.

Loop Unrolling

void unroll2a_combine(vec_ptr v, data_t *dest)
{
    long length = vec_length(v);
    long limit = length-1;
    data_t *d = get_vec_start(v);
    data_t x0 = IDENT;
    data_t x1 = IDENT;
    long i;
    /* Combine 2 elements at a time */
    for (i = 0; i < limit; i+=2) {
        x0 = x0 OP d[i];
        x1 = x1 OP d[i+1];
    }
    /* Finish any remaining elements */
    for (; i < length; i++) {
        x0 = x0 OP d[i];
    }
    *dest = x0 OP x1;
}

Effect of Loop Unrolling — Unroll: Integer Add 0.81 · Integer Mult 1.51 · Double FP Add 1.51 · Double FP Mult 2.51 — Multiple instructions every cycle!

2 × 2 展开: 每次迭代处理两个元素, 而且用两个独立的累加器 x0、x1 (偶数位置和奇数位置各一个), 最后再合并. 两条依赖链可以在不同的功能单元上并行推进, CPE 几乎减半: 整数乘、浮点加 1.51, 浮点乘 2.51, 整数加 0.81 (每个周期不止一条指令). 收尾循环处理元素个数为奇数时剩下的一个. (课件只给出了函数的主要部分, 这里补全了 length、d、i 的声明.)

注意: 对浮点数这样重排改变了运算顺序, 由于浮点加法不满足结合律 (第 1 讲), 结果可能与顺序累加有细微差别, 所以编译器默认不会自动这样做, 需要程序员手写或使用 -ffast-math.

Summary: Getting High Performance — Good compiler and flags · Don't do anything sub-optimal · Watch out for hidden algorithmic inefficiencies · Write compiler-friendly code · Watch out for optimization blockers: procedure calls & memory references · Look carefully at innermost loops (where most work is done) · Tune code for machine · Exploit instruction-level parallelism · Avoid unpredictable branches · Make code cache friendly

编译器优化很容易就能把 CPE 从约 20 降到 3–5; 再结合体系结构知识手工调优 (多累加器、向量化等), 能做到每个周期处理 4–16 个元素, 新的编译器正在缩小这个差距.

总结: 选好编译器和编译选项; 不做明显低效的事 (警惕隐藏的算法低效, 如循环里的 strlen; 写编译器容易优化的代码, 注意函数调用和内存引用这两大优化障碍; 盯住最内层循环); 针对机器调优 (利用指令级并行, 避免难预测的分支, 让代码缓存友好).
