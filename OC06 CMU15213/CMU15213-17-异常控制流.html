Slide 7–9

Control Flow — Processors do only one thing: · From startup to shutdown, each CPU core simply reads and executes (interprets) a sequence of instructions, one at a time * · This sequence is the CPU's control flow (or flow of control) · * Externally, from an architectural viewpoint (internally, the CPU may use parallel out-of-order execution)

Altering the Control Flow — Up to now: two mechanisms for changing control flow: · Jumps and branches · Call and return · React to changes in program state · Insufficient for a useful system: Difficult to react to changes in system state · Data arrives from a disk or a network adapter · Instruction divides by zero · User hits Ctrl-C at the keyboard · System timer expires · System needs mechanisms for “exceptional control flow”

Exceptional Control Flow — Exists at all levels of a computer system · Low level mechanisms · 1. Exceptions · Change in control flow in response to a system event (i.e., change in system state) · Implemented using combination of hardware and OS software · Higher level mechanisms · 2. Process context switch · Implemented by OS software and hardware timer · 3. Signals · Implemented by OS software · 4. Nonlocal jumps: setjmp() and longjmp() · Implemented by C runtime library

到目前为止改变控制流的手段只有两种: 跳转/分支, 调用/返回, 它们只能对程序自身状态的变化作出反应. 这不够: 系统还要对系统状态的变化作出反应, 例如磁盘或网卡来了数据、指令除以零、用户按 Ctrl-C、定时器到期. 这需要异常控制流 (ECF).

ECF 存在于系统的各个层次: 底层是异常 (硬件和操作系统配合实现); 高层有进程上下文切换 (操作系统 + 硬件定时器)、信号 (操作系统软件)、非本地跳转 setjmp/longjmp (C 运行库).

Slide 11–12

Exceptions — An exception is a transfer of control to the OS kernel in response to some event (i.e., change in processor state) · Kernel is the memory-resident part of the OS · Examples of events: Divide by 0, arithmetic overflow, page fault, I/O request completes, typing Ctrl-C

Exception Tables — Each type of event has a unique exception number k · k = index into exception table (a.k.a. interrupt vector) · Handler k is called each time exception k occurs

异常: 因为某个事件 (处理器状态的变化) 把控制转给操作系统内核. 事件例如除以零、算术溢出、缺页、I/O 完成、按 Ctrl-C. 正在执行的指令叫 I_current; 内核的异常处理程序处理完后, 视异常类型, 回到 I_current 重新执行、回到下一条 I_next, 或者中止程序.

每种事件有唯一的异常号 k. 内核启动时建立一张异常表 (也叫中断向量), 第 k 项是处理程序 k 的地址; 发生异常 k 时, 硬件以 k 为下标查表, 跳到对应处理程序.

Slide 13–15

Taxonomy of Hardware ECF — ECF: Asynchronous (Interrupts) · Synchronous (Traps, Faults, Aborts)

Asynchronous Exceptions (Interrupts) — Caused by events external to the processor · Indicated by setting the processor's interrupt pin · Handler returns to “next” instruction · Examples: · Timer interrupt · Every few ms, an external timer chip triggers an interrupt · Used by the kernel to take back control from user programs · I/O interrupt from external device · Hitting Ctrl-C at the keyboard · Arrival of a packet from a network · Arrival of data from a disk

Synchronous Exceptions — Caused by events that occur as a result of executing an instruction: · Traps · Intentional, set program up to “trip the trap” and do something · Examples: system calls, gdb breakpoints · Returns control to “next” instruction · Faults · Unintentional but possibly recoverable · Examples: page faults (recoverable), protection faults (unrecoverable), floating point exceptions · Either re-executes faulting (“current”) instruction or aborts · Aborts · Unintentional and unrecoverable · Examples: illegal instruction, parity error, machine check · Aborts current program

硬件异常分两大类四小类:

类别原因例子处理后
中断 (异步)处理器外部的事件, 通过中断引脚通知定时器中断、键盘 Ctrl-C、网络包到达、磁盘数据到达回到下一条指令
陷阱 (同步)有意的, 由指令故意触发系统调用、gdb 断点回到下一条指令

Almost like a function call · Transfer of control · On return, executes next instruction · Passes arguments using calling convention · Gets result in %rax · One Important exception! · Executed by Kernel · Different set of privileges · And other differences: · E.g., “address” of “function” is in %rax · Uses errno · Etc.

x86-64 Linux 的每个系统调用有唯一编号 (read 0、write 1、open 2、fork 57、execve 59、_exit 60、kill 62). 用户调用 open 时, C 库的 __open 把编号 2 放进 %eax, 执行 syscall 指令陷入内核. 约定: %rax 放调用号, 参数依次放 %rdi、%rsi、%rdx、%r10、%r8、%r9 (第 4 个参数用 %r10 而不是普通函数的 %rcx, 因为 syscall 指令会用 %rcx 保存返回地址); 返回值在 %rax, 负值表示出错, 其绝对值就是 errno. 后面那条 cmp 检查返回值是否落在 −4095 到 −1 的出错范围内.

系统调用很像函数调用 (转移控制、返回后执行下一条、用寄存器传参、结果在 %rax), 但有一个重要区别: 它由内核以更高的特权执行; 另外「函数地址」换成了 %rax 里的编号, 出错通过 errno 报告.

Signals — A signal is a small message that notifies a process that an event of some type has occurred in the system · Akin to exceptions and interrupts · Sent from the kernel (sometimes at the request of another process) to a process · Signal type is identified by small integer ID's (1-30) · Only information in a signal is its ID and the fact that it arrived

信号是一条小消息, 通知进程系统里发生了某类事件. 它类似异常和中断, 但由内核发给进程 (有时是应他进程的请求). 信号只携带一个信息: 它的编号, 以及它到达了这件事. 常见信号: SIGINT (Ctrl-C, 默认终止)、SIGKILL (强制杀死, 不能捕获或忽略)、SIGSEGV (段错误)、SIGALRM (定时器)、SIGCHLD (子进程停止或终止, 默认忽略, 正是解决 shell 问题要用的).

幻灯片小错: "small integer ID's (1-30)" 不准确. Linux 的标准信号是 1–31 (31 为 SIGSYS), 另外还有实时信号 SIGRTMIN–SIGRTMAX (通常 34–64). 教材图 8.26 列出的也是 1–30, 这页沿用了旧数字.

Slide 26–31

Signal Concepts: Sending a Signal — Kernel sends a signal to a destination process by updating some state in the context of the destination process · Kernel sends a signal for one of the following reasons: · Kernel has detected a system event such as divide-by-zero (SIGFPE) or the termination of a child process (SIGCHLD) · Another process has invoked the kill system call to explicitly request the kernel to send a signal to the destination process

(Animation, slides 27–31: Process A sends to C → kernel sets bit in “Pending for C” → Received by C → bit cleared to 0)

发送信号: 内核修改目的进程上下文中的某个状态. 两种原因: 内核检测到系统事件 (除以零发 SIGFPE, 子进程终止发 SIGCHLD); 或者另一个进程调用 kill 系统调用, 请内核向目的进程发信号. 动画演示: 进程 A 向 C 发信号时, 内核把 C 的 pending 位向量里该信号对应的位置 1; C 接收后, 该位清 0.

Slide 32

Signal Concepts: Receiving a Signal — A destination process receives a signal when it is forced by the kernel to react in some way to the signal · Some possible ways to react: · Ignore the signal (do nothing) · Terminate the process (with optional core dump) · Catch the signal by executing a user-level function called signal handler · Akin to a hardware exception handler being called in response to an asynchronous interrupt:

接收信号: 内核强迫目的进程以某种方式对信号作出反应. 三种反应: 忽略; 终止进程 (可能产生 core dump 内存转储文件); 捕获, 即执行一个用户级函数, 叫信号处理程序. 捕获的过程和硬件中断很像: 进程在 I_curr 处收到信号, 控制转到处理程序, 处理程序运行, 返回到下一条指令 I_next 继续.

Slide 33–34

Signal Concepts: Pending and Blocked Signals — A signal is pending if sent but not yet received · There can be at most one pending signal of each type · Important: Signals are not queued · If a process has a pending signal of type k, then subsequent signals of type k that are sent to that process are discarded · A process can block the receipt of certain signals · Blocked signals can be sent, but will not be received until the signal is unblocked · Some signals cannot be blocked (SIGKILL, SIGSTOP) or can only be blocked when sent by other processes (SIGSEGV, SIGILL, etc) · A pending signal is received at most once

Signal Concepts: Pending/Blocked Bits — Kernel maintains pending and blocked bit vectors in the context of each process · pending: represents the set of pending signals · Kernel sets bit k in pending when a signal of type k is sent · Kernel clears bit k in pending when a signal of type k is received · blocked: represents the set of blocked signals · Can be set and cleared by using the sigprocmask function · Also referred to as the signal mask.

已发送但还没被接收的信号叫待处理 (pending). 每种类型最多只有一个待处理信号: 信号不排队. 如果已经有一个 k 类信号待处理, 之后再发来的 k 类信号直接丢弃. 进程可以阻塞某些信号: 被阻塞的信号仍可以发送, 但要等解除阻塞后才会被接收. SIGKILL、SIGSTOP 不能阻塞; SIGSEGV、SIGILL 这类由程序自身错误引起的信号, 只有由别的进程发送时才能被阻塞. 一个待处理信号最多被接收一次.

实现: 内核为每个进程维护两个位向量. pending: 发送 k 类信号时置位 k, 接收时清除. blocked: 被阻塞的信号集合, 用 sigprocmask 设置, 也叫信号掩码.

Slide 40

Sending Signals with kill Function

void fork12()
{
    pid_t pid[N];
    int i;
    int child_status;

    for (i = 0; i < N; i++)
        if ((pid[i] = fork()) == 0) {
            /* Child: Infinite Loop */
            while(1)
                ;
        }

    for (i = 0; i < N; i++) {
        printf("Killing process %d\n", pid[i]);
        kill(pid[i], SIGINT);
    }

    for (i = 0; i < N; i++) {
        pid_t wpid = wait(&child_status);
        if (WIFEXITED(child_status))
            printf("Child %d terminated with exit status %d\n",
                   wpid, WEXITSTATUS(child_status));
        else
            printf("Child %d terminated abnormally\n", wpid);
    }
}

程序中用 kill 函数发信号: kill(pid, sig). fork12 创建 N 个死循环的子进程, 逐个发 SIGINT, 再 wait 回收. 子进程是被信号终止的, 不是正常退出, 所以 WIFEXITED 为假, 每个都打印 "terminated abnormally".

Slide 41–43

Receiving Signals — Suppose kernel is returning from an exception handler and is ready to pass control to process p · Kernel computes pnb = pending & ~blocked · The set of pending nonblocked signals for process p · If (pnb == 0) · Pass control to next instruction in the logical flow for p · Else · Choose least nonzero bit k in pnb and force process p to receive signal k · The receipt of the signal triggers some action by p · Repeat for all nonzero k in pnb · Pass control to next instruction in logical flow for p

Default Actions — Each signal type has a predefined default action, which is one of: · The process terminates · The process stops until restarted by a SIGCONT signal · The process ignores the signal

接收的时机: 内核从异常处理程序返回、准备把控制交给进程 p 时 (例如上下文切换到 p、系统调用返回), 计算 pnb = pending & ~blocked, 即「待处理且未被阻塞」的信号集合. 为空就照常继续 p 的下一条指令; 否则从最小编号的 k 开始, 让 p 依次接收每个信号 k, 触发相应的动作, 然后才回到 p 的下一条指令.

每种信号都有预定义的默认动作: 终止进程; 停止进程直到收到 SIGCONT; 忽略.

Slide 45–46

Installing Signal Handlers — The signal function modifies the default action associated with the receipt of signal signum: · handler_t *signal(int signum, handler_t *handler) · Different values for handler: · SIG_IGN: ignore signals of type signum · SIG_DFL: revert to the default action on receipt of signals of type signum · Otherwise, handler is the address of a user-level signal handler · Called when process receives signal of type signum · Referred to as “installing” the handler · Executing handler is called “catching” or “handling” the signal · When the handler executes its return statement, control passes back to instruction in the control flow of the process that was interrupted by receipt of the signal

Signal Handling Example

void sigint_handler(int sig) /* SIGINT handler */
{
    printf("So you think you can stop the bomb with ctrl-c, do you?\n");
    sleep(2);
    printf("Well...");
    fflush(stdout);
    sleep(1);
    printf("OK. :-)\n");
    exit(0);
}

int main(int argc, char** argv)
{
    /* Install the SIGINT handler */
    if (signal(SIGINT, sigint_handler) == SIG_ERR)
        unix_error("signal error");

    /* Wait for the receipt of a signal */
    pause();

    return 0;
}

用 signal 函数改变信号 signum 的处理方式: SIG_IGN 忽略, SIG_DFL 恢复默认, 其他值是用户函数的地址. 设置用户函数叫安装处理程序, 执行它叫捕获或处理信号. 处理程序 return 后, 控制回到被信号打断的那条指令处继续. SIGKILL 和 SIGSTOP 的动作不能改变.

例子 (仿 bomb lab 的玩笑): 安装 SIGINT 处理程序后 pause() 等待信号. 按 Ctrl-C 时不再直接终止, 而是打印几行字后退出. 注意这个例子在处理程序里用了 printf 和 exit, 后面会讲它们并不安全 (第 55 页给出安全版本).

Slide 47–49

Signals Handlers as Concurrent Flows — A signal handler is a separate logical flow (not process) that runs concurrently with the main program · But, this flow exists only until returns to main program · (Process A: while (1) ; · Process A: handler(){ … } · Process B)

Nested Signal Handlers — Handlers can be interrupted by other handlers

信号处理程序是一条与主程序并发的独立逻辑流 (不是另一个进程), 它只存在到返回主程序为止. 第 48 页的另一种视角: 信号发出时进程 A 可能没在运行 (B 在运行); 下一次切换回 A 时, 内核发现有待处理信号, 先让 A 运行处理程序, 返回后 A 的主程序才从 I_next 继续.

处理程序还可以被另一种信号的处理程序打断, 形成嵌套: 主程序 → S → T → 返回 S → 返回主程序. 因为同一个进程中这些代码交替执行、共享全局变量, 就产生了并发问题.

阻塞信号有两种机制. 隐式: 内核在执行某类信号的处理程序期间, 自动阻塞同类信号, 所以 SIGINT 处理程序不会被另一个 SIGINT 打断 (但会被别的信号打断). 显式: 用 sigprocmask 设置阻塞集合; 配套函数 sigemptyset (清空)、sigfillset (全部加入)、sigaddset (加一个)、sigdelset (删一个) 操作信号集 sigset_t.

临时阻塞的固定写法: 构造只含 SIGINT 的集合; SIG_BLOCK 把它加进阻塞集合, 同时把旧的阻塞集合存进 prev_mask; 执行不想被打断的代码; 最后 SIG_SETMASK 恢复旧集合. 恢复旧集合而不是直接 SIG_UNBLOCK, 是为了不破坏调用前就已经存在的阻塞设置.

Safe Signal Handling — Handlers are tricky because they are concurrent with main program and share the same global data structures · Shared data structures can become corrupted. · We'll explore concurrency issues later in the term · For now here are some guidelines to help you avoid trouble.

Guidelines for Writing Safe Handlers — G0: Keep your handlers as simple as possible · e.g., set a global flag and return · G1: Call only async-signal-safe functions in your handlers · printf, sprintf, malloc, and exit are not safe! · G2: Save and restore errno on entry and exit · So that other handlers don't overwrite your value of errno · G3: Protect accesses to shared data structures by temporarily blocking all signals · To prevent possible corruption · G4: Declare global variables as volatile · To prevent compiler from storing them in a register · G5: Declare global flags as volatile sig_atomic_t · flag: variable that is only read or written (e.g. flag = 1, not flag++) · Flag declared this way does not need to be protected like other globals

处理程序难写, 因为它和主程序并发, 又共享全局数据, 数据可能被破坏. 六条准则:

  • G0 处理程序尽量简单, 例如只设一个全局标志就返回, 其余工作交给主程序.
  • G1 只调用异步信号安全的函数. printf、sprintf、malloc、exit 都不安全: 例如主程序正在 malloc 里修改堆的链表时被打断, 处理程序再调用 malloc 就会看到一半修改过的数据结构; printf 内部有锁和缓冲区, 可能死锁或输出错乱.
  • G2 进入时保存 errno, 退出前恢复: 处理程序中的系统调用可能改写 errno, 而主程序也许正要读它.
  • G3 访问共享数据结构时临时阻塞所有信号.
  • G4 全局变量声明为 volatile, 迫使编译器每次都从内存读写, 不缓存在寄存器里, 否则主程序可能永远看不到处理程序做的修改.
  • G5 标志变量声明为 volatile sig_atomic_t: 对它的单次读或写是原子的, 不会被打断到一半 (只能 flag = 1, 不能 flag++, 后者是读、改、写三步), 这样的标志不需要另外保护.

错误示范: 用 SIGCHLD 给子进程计数. 5 个子进程几乎同时 (都 sleep 1 秒后) 退出. 处理程序每次只 wait 一个, 而且里面还 sleep(1). 处理第一个 SIGCHLD 时, 其余子进程的 SIGCHLD 陆续到来: 第一个变成待处理, 后面的因为信号不排队被直接丢弃. 结果只回收了两个, ccount 停在 3, 父进程永远空转. 结论: 收到一个信号只说明「至少发生了一次」这类事件, 不能用信号计数.

Synchronizing Flows to Avoid Races — SIGCHLD handler for a simple shell · Blocks all signals while running critical code

void handler(int sig)
{
    int olderrno = errno;
    sigset_t mask_all, prev_all;
    pid_t pid;

    sigfillset(&mask_all);
    while ((pid = waitpid(-1, NULL, 0)) > 0) { /* Reap child */
        sigprocmask(SIG_BLOCK, &mask_all, &prev_all);
        deletejob(pid); /* Delete the child from the job list */
        sigprocmask(SIG_SETMASK, &prev_all, NULL);
    }
    if (pid != 0 && errno != ECHILD)
        sio_error("waitpid error");
    errno = olderrno;
}

正确做法: 处理程序里循环 wait, 一次把所有已终止的子进程都回收掉, 直到 wait 返回 −1 且 errno 为 ECHILD (没有子进程了). 这样即使多个 SIGCHLD 合并成一个, 也不会漏. 5 个子进程全部回收.

简单 shell 的 SIGCHLD 处理程序: 回收子进程后从作业列表中删除它. 作业列表是与主程序共享的全局数据, 所以删除时临时阻塞所有信号 (准则 G3).

幻灯片小错: 第 59 页循环后的判断写成 if (pid != 0 && errno != ECHILD). 选项为 0 的 waitpid 只会返回正数或 −1, 永远不会返回 0, 所以 pid != 0 这一条多余 (只有带 WNOHANG 时才可能返回 0). 教材图 8.40 写的是 if (errno != ECHILD).

Corrected Shell Program Without Race

int main(int argc, char **argv)
{
    int pid;
    sigset_t mask_all, mask_one, prev_one;
    int n = N; /* N = 5 */
    sigfillset(&mask_all);
    sigemptyset(&mask_one);
    sigaddset(&mask_one, SIGCHLD);
    signal(SIGCHLD, handler);
    initjobs(); /* Initialize the job list */

    while (n--) {
        sigprocmask(SIG_BLOCK, &mask_one, &prev_one); /* Block SIGCHLD */
        if ((pid = fork()) == 0) { /* Child process */
            sigprocmask(SIG_SETMASK, &prev_one, NULL); /* Unblock SIGCHLD */
            execve("/bin/date", argv, NULL);
        }
        sigprocmask(SIG_BLOCK, &mask_all, NULL); /* Parent process */
        addjob(pid);  /* Add the child to the job list */
        sigprocmask(SIG_SETMASK, &prev_one, NULL);  /* Unblock SIGCHLD */
    }
    exit(0);
}

竞争 (race): 第一版假设父进程在子进程结束之前就执行 addjob. 但子进程可能跑得很快: fork 之后子进程立刻运行 date 并结束, 内核发 SIGCHLD, 父进程在 addjob 之前就进入处理程序, deletejob 删除一个还不在列表里的作业; 之后父进程才 addjob, 列表里就永远留着一个已经不存在的作业. 结果取决于调度顺序, 这就是竞争.

修正: 在 fork 之前阻塞 SIGCHLD, 直到 addjob 完成后才解除. 这样 SIGCHLD 即使提前到来也只是待处理, 要等 addjob 之后才被接收, 保证先加后删. 子进程会继承阻塞集合, 所以子进程在 execve 之前要先解除对 SIGCHLD 的阻塞.

Waiting for Signals with sigsuspend — int sigsuspend(const sigset_t *mask) · Equivalent to atomic (uninterruptable) version of:

sigprocmask(SIG_SETMASK, &mask, &prev);
pause();
sigprocmask(SIG_SETMASK, &prev, NULL);
int main(int argc, char **argv) {
    sigset_t mask, prev;
    int n = N; /* N = 10 */
    signal(SIGCHLD, sigchld_handler);
    signal(SIGINT, sigint_handler);
    sigemptyset(&mask);
    sigaddset(&mask, SIGCHLD);

    while (n--) {
        sigprocmask(SIG_BLOCK, &mask, &prev); /* Block SIGCHLD */
        if (fork() == 0) /* Child */
            exit(0);

        /* Wait for SIGCHLD to be received */
        pid = 0;
        while (!pid)
            sigsuspend(&prev);

        /* Optionally unblock SIGCHLD */
        sigprocmask(SIG_SETMASK, &prev, NULL);
        /* Do some work after receiving SIGCHLD */
        printf(".");
    }
    printf("\n");
    exit(0);
}

sigsuspend(mask) 原子地完成三件事: 临时把阻塞集合换成 mask、pause 等待信号、处理程序返回后恢复原来的阻塞集合. 关键在「原子」: 换掩码和开始睡眠之间不会有信号插进来.

用法: 检查 pid 时 SIGCHLD 一直被阻塞, 所以检查之后不会有信号溜进来; sigsuspend(&prev) 用不阻塞 SIGCHLD 的旧掩码睡眠, 此时到来的 SIGCHLD (包括之前已待处理的) 立即被接收, 处理程序设置 pid, sigsuspend 返回时又恢复为阻塞 SIGCHLD 的状态; 循环检查 pid, 不为 0 就退出. 既没有竞争, 也不忙等、不延迟. 循环中用 while 而不是 if, 是因为别的信号 (如 SIGINT) 也会让 sigsuspend 返回. 这正是 shell lab 等待前台作业的标准写法.
