给线程传参数
Passing Argument(s) to a Thread

Slide 9

3 right & 1 wrong way to Pass Thread Arg — Unique Pointer · Global array, one entry per thread · Pass pointer to thread's entry to pthread_create (as 4th arg) · Cast of int/long · Producer casts an int/long to void*, passes to pthread_create · Consumer casts void* argument back to int/long · Works for small amounts of data (one number) · Malloc/free · Producer malloc's space, passes pointer to pthread_create · Consumer dereferences pointer, frees space · Always works; necessary for passing large amounts of data · INCORRECT: Pointer to stack address · Producer passes address to producer's stack in pthread_create · Consumer dereferences pointer

给线程传参的三种正确方法和一种错误方法: ① 唯一指针: 一个全局数组, 每个线程一项, 把该项的地址作为 pthread_create 的第 4 个参数; ② 整数强制转换: 把 int/long 转成 void* 传过去, 线程再转回来, 只适合传一个数; ③ malloc/free: 创建者 malloc 一块内存传指针, 线程读完后 free, 总是可行, 传大量数据 (结构体) 时必须用它; ④ 错误: 传创建者栈上变量的地址, 线程再去解引用.

Passing an argument to a thread (1/4) - OK

int hist[N] = {0};

int main(int argc, char *argv[]) {
    long i;
    pthread_t tids[N];

    for (i = 0; i < N; i++)
        Pthread_create(&tids[i],
                       NULL,
                       thread,
                       &hist[i]);
    for (i = 0; i < N; i++)
        Pthread_join(tids[i], NULL);
    check();
}

void *thread(void *vargp)
{
    *(int *)vargp += 1;
    return NULL;
}

void check(void) {
    for (int i=0; i<N; i++) {
        if (hist[i] != 1) {
            printf("Failed at %d\n", i);
            exit(-1);
        }
    }
    printf("OK\n");
}

Each thread receives a unique pointer

Passing an argument to a thread (2/4) – OK

    for (i = 0; i < N; i++)
        Pthread_create(&tids[i],
                       NULL,
                       thread,
                       (void *)i);

void *thread(void *vargp)
{
    hist[(long)vargp] += 1;
    return NULL;
}

Each thread receives a unique array index as a value · Casting from long to void* and back is safe

测试框架: 有 N 个线程, 每个线程把 hist 中「属于自己」的那一项加 1; 全部 join 之后, check 检查每项是否恰好为 1. 若两个线程拿到同一个下标, 就会有一项是 2、另一项是 0.

方法 1: 传 &hist[i], 每个线程拿到不同的指针. 方法 2: 直接把下标 i (long) 转成 void* 传值, 线程再转回 long. 在 x86-64 上 long 和指针都是 64 位, 来回转换不丢信息, 所以安全; 传的是值, 不是地址, 不存在共享.

错误方法: 传 &i. 所有线程拿到的都是主线程栈上同一个 i 的地址; 线程读取 *vargp 时, 主线程可能已经 i++ 了, 于是某些下标被读两次、某些一次也没读到 (上一讲的竞争测试). 甚至可能在第二个循环 (join) 重新把 i 从 0 开始数时才读到.

共享与数据竞争
Sharing and Data Races

Slide 15–17

Shared Variables in Threaded C Programs — Question: Which variables in a threaded C program are shared? · The answer is not as simple as “global variables are shared” and “stack variables are private” · Def: A variable x is shared if and only if multiple threads reference some instance of x. · Requires answers to the following questions: · What is the memory model for threads? · How are instances of variables mapped to memory? · How many threads might reference each of these instances?

Threads Memory Model: Conceptual — Multiple threads run within the context of a single process · Each thread has its own separate thread context · Thread ID, stack, stack pointer, PC, condition codes, and GP registers · All threads share the remaining process context · Code, data, heap, and shared library segments of the process virtual address space · Open files and installed handlers

Threads Memory Model: Actual — Separation of data is not strictly enforced: · Register values are truly separate and protected, but… · Any thread can read and write the stack of any other thread · The mismatch between the conceptual and operation model is a source of confusion and errors

多线程 C 程序中哪些变量是共享的? 不能简单地说「全局变量共享、栈上变量私有». 定义: 变量 x 是共享的, 当且仅当有多个线程引用了 x 的某个实例. 要回答这个问题需要知道三件事: 线程的内存模型、变量实例如何映射到内存、每个实例可能被几个线程引用.

概念上的内存模型: 每个线程有自己的线程上下文 (线程 ID、栈、栈指针、PC、条件码、通用寄存器); 其余进程上下文全部共享 (代码、数据、堆、共享库段, 打开的文件, 安装的信号处理程序). 实际上: 只有寄存器是真正分开并受保护的; 栈并没有隔离, 任何线程都可以读写别的线程的栈. 概念模型与实际模型的不一致是困惑和错误的来源.

Slide 19–21

Mapping Variable Instances to Memory — Global variables · Variable declared outside of a function · Virtual memory contains exactly one instance of any global variable · Local automatic variables · Variable declared inside function without static attribute · Each thread stack contains one instance of each local variable · Local static variables · Variable declared inside function with the static attribute · Virtual memory contains exactly one instance of any local static variable. · errno is special · Declared outside a function, but each thread stack contains one instance

char **ptr; /* global var */

int main(int main, char *argv[])
{
    long i;
    pthread_t tid;
    char *msgs[2] = {
        "Hello from foo",
        "Hello from bar"
    };

    ptr = msgs;
    for (i = 0; i < 2; i++)
        Pthread_create(&tid,
                       NULL,
                       thread,
                       (void *)i);
    Pthread_exit(NULL);
}

void *thread(void *vargp)
{
    long myid = (long)vargp;
    static int cnt = 0;

    printf("[%ld]:  %s (cnt=%d)\n",
           myid, ptr[myid], ++cnt);
    return NULL;
}

Global var: 1 instance (ptr [data]) · Local auto vars: 1 instance (i.m, msgs.m, tid.m) · Local auto var: 2 instances (myid.p0 [peer thread 0's stack], myid.p1 [peer thread 1's stack]) · Local static var: 1 instance (cnt [data])

变量实例与内存的对应: 全局变量 (函数外声明) 在虚拟内存中恰好一个实例; 局部自动变量 (函数内、无 static) 每个线程的栈上各有一个实例; 局部静态变量 (函数内、有 static) 只有一个实例, 和全局变量一样在数据段. errno 特殊: 看起来是全局的, 但每个线程有自己的一份.

例 sharing.c: 全局变量 ptr 一个实例; main 的局部变量 i、msgs、tid 各一个实例 (在主线程栈上, 记作 i.m 等); 线程函数的局部变量 myid 有两个实例, 分别在两个对等线程的栈上 (myid.p0、myid.p1); 静态变量 cnt 一个实例. 主线程最后调用 Pthread_exit 而不是 return: 这样只结束主线程, 进程继续, 两个对等线程能运行完 (若 return, 整个进程立即结束). 注意 msgs 是主线程栈上的数组, 线程通过全局指针 ptr 访问它, 所以主线程不能先返回.

幻灯片小错: ① int main(int main, char *argv[]) 把第一个参数命名成了 main, 应为 argc (教材图 12.15 为 int main()). ② "errno … each thread stack contains one instance" 不准确: 多线程程序中 errno 是线程局部存储 (glibc 把它定义为宏 (*__errno_location())), 每个线程一份, 但不在线程的栈上, 而在线程局部存储区.

Answer: A variable x is shared iff multiple threads reference at least one instance of x. Thus: · ptr, cnt, and msgs are shared · i and myid are not shared

逐个分析: ptr 被三个线程引用; cnt 被两个对等线程引用 (++cnt); i 只有主线程用 (传给线程的是 i 的值, 不是地址); msgs 虽是主线程的局部变量, 但对等线程通过 ptr[myid] 读它, 所以被三个线程引用; myid 的两个实例各只被一个线程引用. 结论: ptr、cnt、msgs 共享, i、myid 不共享. msgs 就是「栈上变量也能被共享」的例子. 另外 cnt 被两个线程同时 ++, 本身就有数据竞争.

Synchronizing Threads — Shared variables are handy... · …but you risk data races and synchronization errors.

static unsigned long cnt = 0;

void *incr_thread(void *arg) {
    unsigned long i;
    unsigned long niters =
        (unsigned long) arg;

    for (i = 0; i < niters; i++) {
        cnt++;
    }
}

int main(int argc, char **argv) {
    unsigned long niters =
        strtoul(argv[1], NULL, 10);

    pthread_t t1, t2;
    Pthread_create(&t1, NULL,
                   incr_thread,
                   (void *)niters);
    Pthread_create(&t2, NULL,
                   incr_thread,
                   (void *)niters);
    Pthread_join(&t1, NULL);
    Pthread_join(&t2, NULL);
    if (cnt != 2*niters) {
        printf("FAIL: cnt=%lu not %lu\n",
               cnt, 2*niters;
        return 1;
    } else {
        printf("OK: cnt=%lu\n", cnt);
    }
    return 0;
}

共享变量很方便, 但有数据竞争和同步错误的风险. 演示 1: 两个线程各把共享计数器 cnt 加 niters 次 (例如各 10000 次), 预期 cnt = 20000, 实际运行常常得到更小的数, 而且每次不同.

幻灯片代码错误 (两处): ① Pthread_join(&t1, NULL): pthread_join 的第一个参数是 pthread_t 值, 不是地址, 应为 Pthread_join(t1, NULL) (pthread_create 才取地址). ② printf("FAIL: …", cnt, 2*niters; 少了右括号, 应为 2*niters);. 两处都无法通过编译. 另外 incr_thread 声明返回 void * 却没有 return 语句 (C 允许编译, 但调用者若使用返回值就是未定义行为).

Slide 30–31

Progress Graphs — A progress graph depicts the discrete execution state space of concurrent threads. · Each axis corresponds to the sequential order of instructions in a thread. · Each point corresponds to a possible execution state (Inst1, Inst2). · E.g., (L1, S2) denotes state where thread 1 has completed L1 and thread 2 has completed S2.

Trajectories in Progress Graphs — A trajectory is a sequence of legal state transitions that describes one possible concurrent execution of the threads. · Example: H1, L1, U1, H2, L2, S1, T1, U2, S2, T2

进度图描述两个并发线程的执行状态空间: 横轴是线程 1 的指令序列, 纵轴是线程 2 的; 网格上的点 (I1, I2) 表示线程 1 已完成 I1、线程 2 已完成 I2 的状态. 一次执行就是一条轨迹: 从原点出发, 每一步向右 (线程 1 执行一条指令) 或向上 (线程 2 执行一条), 单核上不会斜走. 第 31 页的轨迹正是上一页出错的那种顺序.

Slide 32–33

Critical Sections and Unsafe Regions — L, U, and S form a critical section with respect to the shared variable cnt · Instructions in critical sections (wrt some shared variable) should not be interleaved · Sets of states where such interleaving occurs form unsafe regions

Def: A trajectory is safe iff it does not enter any unsafe region · Claim: A trajectory is correct (wrt cnt) iff it is safe

对共享变量 cnt 来说, 每个线程的 L、U、S 构成一个临界区: 两个线程的临界区内的指令不能交错. 交错发生的那些状态在进度图上围成一个矩形, 叫不安全区 (两个线程都处在临界区中间). 不进入任何不安全区的轨迹是安全的; 结论: 一条轨迹是正确的, 当且仅当它是安全的. 绿色轨迹从不安全区上方或右方绕过 (一个线程整段做完另一个才开始), 红色轨迹穿过它, 就会丢失更新.

互斥锁
Fixing Data Races: Mutexes

Slide 36–37

Enforcing Mutual Exclusion — Question: How can we guarantee a safe trajectory? · Answer: We must synchronize the execution of the threads so that they can never have an unsafe trajectory. · Need to guarantee mutually exclusive access to each critical section.

static unsigned long cnt = 0;
static pthread_mutex_t lock =
    PTHREAD_MUTEX_INITIALIZER;

void *incr_thread(void *arg) {
    unsigned long i;
    unsigned long niters =
        (unsigned long) arg;

    for (i = 0; i < niters; i++) {
        pthread_mutex_lock(&lock);
        cnt++;
        pthread_mutex_unlock(&lock);
    }
}

Coding demo 2: Counting to 20,000 correctly (with threads and a mutex)

MUTual EXclusion (mutex) — Mutex: opaque object which is either locked or unlocked · Boolean value, but cannot do math on it · Starts out unlocked · Two operations: · lock(m) · If the mutex is currently not locked, lock it and return · Otherwise, wait until it becomes unlocked, then retry · unlock(m) · Can only be called when mutex is locked, by the code that locked it · Change mutex to unlocked

怎样保证轨迹安全? 必须同步各线程的执行, 使它们不可能走出不安全的轨迹, 也就是保证对每个临界区的互斥访问: 同一时刻最多一个线程在临界区里. 演示 2: 在 cnt++ 前后加锁和解锁, 结果总是 20000.

互斥锁 (mutex, 取自 MUTual EXclusion): 一个不透明对象, 只有「锁住」和「未锁」两个状态, 初始未锁. lock(m): 若未锁就锁上并返回, 否则等它解锁后再试. unlock(m): 只能由锁住它的那段代码调用, 把它变回未锁. Pthreads 中用 PTHREAD_MUTEX_INITIALIZER 静态初始化.

Slide 38–40

Why Mutexes Work — Provide mutually exclusive access to shared variable by surrounding critical section with lock and unlock operations · Mutex invariant creates a forbidden region that encloses unsafe region and that cannot be entered by any trajectory.

The Cost of Mutexes — (chart: elapsed time vs. number of iterations: no locking (racey) 0.48 s · mutex 15 s)

为什么互斥锁有效: 把 m 看成初值为 1 的计数, lock 减 1, unlock 加 1, 不变式要求 m ≥ 0. 在两个线程都已 lock、都没 unlock 的那些状态, m 将是 −1, 不允许出现, 这些状态构成禁止区, 正好把不安全区包在里面. 任何轨迹都进不去禁止区, 也就进不了不安全区.

代价: 同样的计数, 不加锁 (结果错误) 只要 0.48 秒, 加互斥锁要 15 秒, 慢了约 30 倍. 原因是每次加锁解锁都要执行原子指令, 两个线程还在不同核之间争抢同一把锁和同一条缓存行.

信号量
Semaphores

Slide 42–43

Semaphores — Semaphore: generalization of mutex · Unsigned integer value, but cannot do math on it. · Created with some value >= 0 · Two operations: · P(s) [“Prolaag,” Dutch shorthand for “try to reduce”] · If s is zero, wait for a V operation to happen. · Then subtract 1 from s and return. · V(s) [“Verhogen,” Dutch for “increase”] · Add 1 to s. · If there are any threads waiting inside a P operation, resume one of them · Unlike mutexes, no requirement to call P before calling V

C Semaphore Operations — Pthreads functions:

#include <semaphore.h>

int sem_wait(sem_t *s);  /* P(s) */
int sem_post(sem_t *s);  /* V(s) */

int sem_init(sem_t *s, int pshared, unsigned int val);

(pshared:) Share among processes? (normally you want to pass zero, see manpage for details) · (val:) Initial semaphore value

信号量 (Dijkstra 提出) 是互斥锁的推广: 一个非负整数, 创建时给初值, 只能用两种操作改变. P(s) (荷兰语 Prolaag, 「试着减少」的缩写): 若 s 为 0 就等待某个 V 操作发生, 然后 s 减 1 返回. V(s) (荷兰语 Verhogen, 「增加»): s 加 1, 若有线程在 P 中等待, 唤醒其中一个. 与互斥锁不同, 不要求先 P 后 V, 任何线程都可以 V.

C 中对应 sem_wait (P)、sem_post (V)、sem_init. sem_init 的 pshared 表示是否在进程之间共享, 通常传 0 (只在本进程的线程间共享); val 是初值. 初值为 1 的信号量叫二元信号量, 可以当互斥锁用.

Semaphore Example

static unsigned long cnt = 0;
static sem_t lock;

void *incr_thread(void *arg) {
    unsigned long i;
    unsigned long niters =
        (unsigned long) arg;

    for (i = 0; i < niters; i++) {
        sem_wait(&lock);
        cnt++;
        sem_post(&lock);
    }
}

    unsigned long niters =
        strtoul(argv[1], NULL, 10);
    sem_init(&lock, 0, 1);
    // ...
}

The Cost of Atomic Memory Operations

原子内存操作: 硬件提供的特殊指令 (测试并设置、比较并交换、交换并相加……), 在内存上完成一整个「读、改、写», 由硬件保证不会被别的核插进来. 互斥锁、信号量本身就是用它们实现的. 只想给计数器加 1 时, 可以直接用: C11 中把 cnt 声明为 _Atomic, cnt++ 就编译成一条带 lock 前缀的 addq, 原来的三条指令变成一条不可分割的指令.

耗时: 原子操作 3.41 秒, 比不加锁慢约 7 倍 (lock 前缀要独占缓存行), 但比互斥锁快 4 倍多, 比信号量快 8 倍.

Summary — Access shared variables with care to avoid data races. · Crucial to understand which variables are shared in the first place · Avoid sharing, if you can · Avoid writing from multiple threads, if you can · Mutexes help, but… · They're slow · (Next time: They can cause problems as well as solve them) · Don't use a semaphore when a mutex will do · They're even slower · (Next time: When is a semaphore actually useful?) · Atomic memory ops are handy, but… · The hardware might not provide the operation you need · (Later courses: Tricky to use correctly)

Mutex implementation (partial)

/**
 * void pthread_mutex_lock(pthread_mutex_t *mtx)
 * Lock the mutex pointed to by MTX. If it is already locked,
 * first sleep until it becomes unlocked.
 */
pthread_mutex_lock:
    call    gettid                          // current thread ID now in %eax
    mov     $1, %edx                        // increment
    lock xadd %edx, MUTEX_CONTENDERS(%rdi)
    // %edx now holds _previous_ value of mtx->contenders
    test    %edx, %edx
    jne     .Lcontended
    // The lock was unlocked, and now we hold it.
    mov     %eax, MUTEX_HOLDER(%rdi)
    ret
.Lcontended:
    // Sleep until another thread calls pthread_mutex_unlock
    // (30 more machine instructions and a system call)

Just one of many ways to implement (discussed in 15-410, -418, etc) · All require assistance from the CPU (special instructions)

Semaphore implementation (partial)

/**
 * void sem_wait(sem_t *sem)
 * Decrement the count of the semaphore pointed to by SEM. If this
 * would make the count negative, first sleep until it is possible to
 * decrement the count without making it negative.
 */
sem_wait:
    mov     $-1, %edx                       // decrement
    lock xadd %edx, SEM_COUNT(%rdi)
    // %edx now holds _previous_ value of sem->count
    test    %edx, %edx
    jle     .Lclosed
    // The semaphore was open.
    ret
.Lclosed:
    // Sleep until another thread calls sem_post
    // (30 more machine instructions and a system call)

Suspiciously similar to a mutex, huh? · (This implementation makes sem_post do most of the work)

Semaphore Usage — As they are more expensive than mutex, don't use them as mutexes · Semaphores instead provide wait on event · Think about our usage of sigsuspend to solve waiting · Thought exercise: · How would you use mutexes versus semaphores to implement waiting on office hour queue? · Bonus: Look up condition variables

互斥锁的一种实现: lock xadd 原子地把 contenders (争用者计数) 加 1 并取回旧值; 旧值为 0 说明锁原来空闲, 现在归我, 记下持有者线程号后返回; 否则进入争用路径, 睡眠直到别的线程解锁 (还要约 30 条指令和一次系统调用). 不争用时只要几条指令. 所有实现都离不开 CPU 的特殊指令.

信号量 sem_wait 几乎一样: lock xadd 原子地把计数减 1 并取回旧值, 旧值 ≤ 0 说明原来已无余量, 去睡眠等待 sem_post; 这个实现把大部分工作交给 sem_post.

信号量的真正用途不是当锁, 而是等待事件, 类似第 17 讲用 sigsuspend 等待信号. 思考题: 用互斥锁和用信号量分别怎样实现答疑排队? 延伸阅读: 条件变量.
