It's Important to Understand How Things Work

  • Why do I need to know this stuff?
    • Abstraction is good, but don't forget reality
  • Most CS and CE courses emphasize abstraction; so do we!
    • Abstract data types
    • Asymptotic analysis
  • But it's helpful to understand what abstractions build upon and their limits!
    • Especially in the presence of bugs
    • Need to understand details of underlying implementations
    • Sometimes the abstract interfaces don't provide the level of control or performance you need

为什么要懂底层: abstraction 抽象 (抽象数据类型、渐近分析) 很好, 这门课也重视它, 但不能忘了现实. 要知道抽象建立在什么之上、在哪里失效. 尤其是出 bug 时, 必须看懂底层实现的细节; 有时抽象接口给不了你需要的控制力或性能. 下面五条「现实」(Great Realities) 就是抽象失效的典型场合.

Slide 6

Reality Example #1: Ints are not Integers, Floats are not Reals

  • Example 1: Is x² ≥ 0?
    • Float's: Yes!
    • Int's:
      • 40000 * 40000 --> 1600000000
      • 50000 * 50000 --> ?
  • Example 2: Is (x + y) + z = x + (y + z)?
    • Unsigned & Signed Int's: Yes!
    • Float's:
      • (1e20 + -1e20) + 3.14 --> 3.14
      • 1e20 + (-1e20 + 3.14) --> ??

(Source: xkcd.com/571)

现实一: int 不是数学上的整数, float 不是实数.

  • x² ≥ 0 吗? 浮点数: 是. int: 40000 × 40000 = 1600000000 正常; 50000 × 50000 = 2500000000 超过 32 位 int 的最大值 2³¹ − 1 ≈ 2.1 × 10⁹, 溢出后得到 −1794967296, 是负数.
  • 加法满足结合律吗? 整数 (有符号、无符号) 满足, 即使溢出也满足. 浮点数不满足: (1e20 + −1e20) + 3.14 = 3.14, 而 1e20 + (−1e20 + 3.14) = 0, 因为 3.14 相对 1e20 太小, 在 −1e20 + 3.14 中被舍入掉了.

两个结果都用 Python 按 32 位整数和双精度浮点核对过.

Slide 7

Computer Arithmetic

  • Does not generate random values
    • Arithmetic operations have important mathematical properties
  • Cannot assume all “usual” mathematical properties
    • Due to finiteness of representations
    • Integer operations satisfy “ring” properties
      • Commutativity, associativity, distributivity
    • Floating point operations satisfy “ordering” properties
      • Monotonicity, values of signs
  • Observation
    • Need to understand which abstractions apply in which contexts
    • Important issues for compiler writers and serious application programmers

计算机算术不是乱来的, 它有确定的数学性质, 只是因为表示是有限的, 不能假设所有「通常」的性质都成立. 整数运算满足环的性质: 交换律、结合律、分配律 (在模 2ʷ 意义下); 浮点运算满足序的性质: 单调性、符号规律 (如 a ≥ b 则 a + c ≥ b + c, 正数乘正数为正), 但不满足结合律. 编译器作者和严肃的应用程序员必须清楚哪些性质在哪种情况下可用 (例如编译器不能随意重排浮点加法).

Slide 8

You've Got to Know Assembly

  • Chances are, you'll never write programs in assembly
    • Compilers are much better & more patient than you are
  • But: Understanding assembly is key to machine-level execution model
    • Behavior of programs in presence of bugs
      • High-level language models break down
    • Tuning program performance
      • Understand optimizations done / not done by the compiler
      • Understanding sources of program inefficiency
    • Implementing system software
      • Compiler has machine code as target
      • Operating systems must manage process state
    • Creating / fighting malware
      • x86 assembly is the language of choice!

现实二: 必须懂汇编. 你多半不会亲手写汇编程序 (编译器比人更好、更有耐心), 但读懂汇编是理解程序在机器层面如何执行的关键: 程序出 bug 时高级语言的模型会失效; 调优时要知道编译器做了和没做哪些优化、低效来自哪里; 编写系统软件时, 编译器的目标就是机器码, 操作系统要管理进程状态; 编写或对抗恶意软件时, x86 汇编是首选语言 (本课的 bomblab、attacklab 就是这方面的练习).

Slide 9

Great Reality #3: Memory Matters — Random Access Memory Is an Unphysical Abstraction

  • Memory is not unbounded
    • It must be allocated and managed
    • Many applications are memory dominated
  • Memory referencing bugs especially pernicious
    • Effects are distant in both time and space
  • Memory performance is not uniform
    • Cache and virtual memory effects can greatly affect program performance
    • Adapting program to characteristics of memory system can lead to major speed improvements

现实三: 内存很重要. 「随机访问内存」(任何地址访问代价相同、容量无限) 是一个不符合物理的抽象. 实际上: 内存有限, 要分配和管理, 很多程序的瓶颈就在内存; 内存引用错误特别阴险, 因为后果在时间和空间上都离出错的地方很远; 内存性能不均匀, 缓存和虚拟内存会大幅影响程序速度, 让程序适应内存系统的特点能显著提速.

Memory Referencing Bug Example

typedef struct {
  int a[2];
  double d;
} struct_t;

double fun(int i) {
  volatile struct_t s;
  s.d = 3.14;
  s.a[i] = 1073741824; /* Possibly out of bounds */
  return s.d;
}
fun(0) --> 3.14
fun(1) --> 3.14
fun(2) --> 3.1399998664856
fun(3) --> 2.00000061035156
fun(4) --> 3.14
fun(6) --> Segmentation fault

Result is system specific

内存引用 bug 的例子. 结构体里 a[2] 之后紧跟 double d, 在栈上从低地址到高地址依次是 a[0]、a[1]、d 的低 4 字节 (d3…d0)、d 的高 4 字节 (d7…d4), 再往上是别的栈内容. C 不检查数组越界, 所以:

  • i = 0, 1: 写的是数组本身, d 不受影响, 返回 3.14.
  • i = 2: 把 1073741824 (= 0x40000000) 写进了 d 的低 4 字节. 3.14 的位模式是 0x40091EB851EB851F, 被改成 0x40091EB840000000, 只动了尾数的低位, 结果 3.1399998664856.
  • i = 3: 写进 d 的高 4 字节, 符号、指数和尾数高位全变了, 变成 0x4000000051EB851F ≈ 2.00000061035156.
  • i = 4、5: 写到结构体之外的栈空间, 这次碰巧没影响 d.
  • i = 6: 改坏了「关键状态」(如保存的返回地址), 函数返回时崩溃: Segmentation fault.

i = 2、3 的两个值用 Python 按小端序改写字节核对过. 具体结果依赖系统 (结构体布局、栈上其他内容); volatile 阻止编译器把 s 优化到寄存器里, 保证真的在内存中读写.

Slide 12

Memory Referencing Errors

  • C and C++ do not provide any memory protection
    • Out of bounds array references
    • Invalid pointer values
    • Abuses of malloc/free
  • Can lead to nasty bugs
    • Whether or not bug has any effect depends on system and compiler
    • Action at a distance
      • Corrupted object logically unrelated to one being accessed
      • Effect of bug may be first observed long after it is generated
  • How can I deal with this?
    • Program in Java, Ruby, Python, ML, …
    • Understand what possible interactions may occur
    • Use or develop tools to detect referencing errors (e.g. Valgrind)

C 和 C++ 不提供内存保护: 数组越界、无效指针、malloc/free 误用都不会被拦下. 后果: bug 是否显现取决于系统和编译器; 「超距作用」, 被破坏的对象和正在访问的对象在逻辑上毫无关系, 而且可能很久之后才暴露. 对策: 用有内存安全保证的语言 (Java、Python、ML 等); 理解可能发生哪些相互影响; 使用或开发检测工具, 如 Valgrind.

Slide 13

Great Reality #4: There's more to performance than asymptotic complexity

  • Constant factors matter too!
  • And even exact op count does not predict performance
    • Easily see 10:1 performance range depending on how code written
    • Must optimize at multiple levels: algorithm, data representations, procedures, and loops
  • Must understand system to optimize performance
    • How programs compiled and executed
    • How to measure program performance and identify bottlenecks
    • How to improve performance without destroying code modularity and generality

现实四: 性能不只是渐近复杂度. 常数因子也重要; 甚至精确的运算次数都不能预测性能, 同样的运算量, 写法不同就能差 10 倍. 优化要在多个层次进行: 算法、数据表示、过程、循环. 要理解程序如何被编译和执行, 如何测量性能、找到瓶颈, 以及如何在不破坏模块化和通用性的前提下提速.

Slide 14–15

Memory System Performance Example

void copyij(int src[2048][2048],
            int dst[2048][2048])
{
  int i,j;
  for (i = 0; i < 2048; i++)
    for (j = 0; j < 2048; j++)
      dst[i][j] = src[i][j];
}

void copyji(int src[2048][2048],
            int dst[2048][2048])
{
  int i,j;
  for (j = 0; j < 2048; j++)
    for (i = 0; i < 2048; i++)
      dst[i][j] = src[i][j];
}

copyij: 4.3ms · copyji: 81.8ms (2.0 GHz Intel Core i7 Haswell)

  • Hierarchical memory organization
  • Performance depends on access patterns
    • Including how step through multi-dimensional array

Learn why on Sept 23: Memory Hierarchy

两个函数做同样的事 (复制 2048 × 2048 的 int 数组), 只是循环顺序不同, 运算次数完全一样, 时间却差约 19 倍 (4.3 ms 对 81.8 ms). 原因: C 的二维数组按行优先存放, copyij 按行扫, 每次访问相邻地址 (步长 1), 能充分利用缓存; copyji 按列扫, 相邻两次访问相隔一整行 2048 × 4 = 8 KB, 几乎每次都缓存不命中.

读图: 「存储器山」的两个水平轴是步长 (×8 字节) 和工作集大小, 纵轴是读吞吐量. 步长越小、数据越能放进缓存, 吞吐量越高. copyij 在左侧山脊上 (步长 1), copyji 在右下角的谷底 (大步长、32 MB 数据). 这张图在第 9 讲「存储器层次」详细解释.

幻灯片小错: 标题 "Learn why on Sept 23" 是秋季学期的日期, 这份课件用于 2026 年春季, 日期没有更新. 存储器层次是本课程第 9 讲.

Slide 16

Great Reality #5: Computers do more than execute programs

  • They need to get data in and out
    • I/O system critical to program reliability and performance
  • They communicate with each other over networks
    • Many system-level issues arise in presence of network
      • Concurrent operations by autonomous processes
      • Coping with unreliable media
      • Cross platform compatibility
      • Complex performance issues

现实五: 计算机不只是执行程序. 它要输入输出数据, I/O 系统对程序的可靠性和性能至关重要; 它们还通过网络相互通信, 由此产生许多系统层面的问题: 多个独立进程的并发操作、应对不可靠的传输介质、跨平台兼容、复杂的性能问题. 这些在课程后半部分 (系统 I/O、网络编程、并发) 讲.

Slide 39

Version Control: Quick Tips

  • Always commit your changes and only your changes
  • Do not do:
    • git add .
      • This adds / commits all files that git is either not tracking or have changed
    • git commit –a
      • This commits all files that have changed, which might include accidental edits
  • Do:
    • git commit <list of files>
      • This commits a specific list of files (usually one) and allows you to write a multi-line commit message

版本控制的小建议: 每次只提交自己有意修改的文件. 不要用 git add . (会把所有未跟踪或改动过的文件都加进来) 和 git commit -a (会提交所有改动, 包括不小心的编辑); 而是用 git commit 文件列表 只提交指定的文件, 并写多行提交说明. 课程从 cache lab 开始用 GitHub Classroom 发布实验, 并以提交历史作为独立完成的证据.
