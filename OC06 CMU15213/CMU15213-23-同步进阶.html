Review: Races, Mutual Exclusion

Slide 3–5

Today — Review: Races, Mutual Exclusion (CSAPP 12.5.1, 12.7.4) · Deadlock (CSAPP 12.7.5) · Semaphores, Events, and Queues (CSAPP 12.5.4) · Reader-Writer Locks and Starvation (CSAPP 12.5.4) · Thread-Safe API Design (CSAPP 12.7.1-12.7.3)

Races — A race occurs when correctness of the program depends on one thread reaching point x before another thread reaches point y

int cnt;

int main(int argc, char** argv) {
    pthread_t t1, t2;
    Pthread_create(&t1, NULL, thread, NULL);
    Pthread_create(&t2, NULL, thread, NULL);
    Pthread_join(t1, NULL);
    Pthread_join(t2, NULL);
    return (counter != 20000);
}

/* thread routine */
void *thread(void *vargp) {
    for (int i = 0; i < 10000; i++)
        cnt++;
    return NULL;
}

(progress graph: safe / unsafe trajectories around the unsafe region) · Some races can be fixed with mutual exclusion

pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void *thread(void *vargp) {
    for (int i = 0; i < 10000; i++) {
        pthread_mutex_lock(&lock);
        cnt++;
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

本讲: 回顾竞争与互斥; 死锁; 信号量、事件和队列; 读写锁与饥饿; 线程安全的 API 设计.

竞争: 程序的正确性依赖于一个线程先到达点 x、另一个线程后到达点 y. 上一讲的计数器例子: 两个线程各加 10000 次, 轨迹穿过不安全区就会出错. 一部分竞争可以用互斥锁修复: 把 cnt++ 包在 lock/unlock 之间.

幻灯片小错: ① 标题页日期 "23rd Lecture, Nov 25, 2025" 是秋季学期的. ② 例子中全局变量叫 cnt, main 却返回 counter != 20000, 变量名不一致, 无法编译.

Slide 6–9

Not all races can be addressed with mutual exclusion

int main(int argc, char** argv) {
    pthread_t tid[N];
    int i;
    for (i = 0; i < N; i++)
        Pthread_create(&tid[i], NULL, thread, &i);
    for (i = 0; i < N; i++)
        Pthread_join(tid[i], NULL);
    return 0;
}

/* thread routine */
void *thread(void *vargp) {
    int myid = *(int *)vargp;
    printf("Hello from thread %d\n", myid);
    return NULL;
}

This race can be fixed by copying data

Pthread_create(&tid[i], NULL, thread, (void *)i);
…
int myid = (int)vargp;

This race can also be fixed with a semaphore

sem_t sem;

int main(int argc, char** argv) {
    pthread_t tid[N];
    int i;
    Sem_init(&sem, 0, 0); // initially closed
    for (i = 0; i < N; i++) {
        Pthread_create(&tid[i], NULL, thread, &i);
        sem_wait(&sem);
    }
    for (i = 0; i < N; i++)
        Pthread_join(tid[i], NULL);
    return 0;
}

void *thread(void *vargp) {
    int myid = *(int *)vargp;
    sem_post(&sem);
    printf("Hello from thread %d\n", myid);
    return NULL;
}

Can't do this with a mutex. Why? · Only thread that locked the mutex can unlock it

并非所有竞争都能用互斥锁解决. 传 &i 的例子: 竞争在于新线程读 *vargp 必须发生在主线程 i++ 之前, 这是先后顺序的要求, 不是「不能同时」的要求, 互斥锁管不了.

修复 1: 复制数据, 直接把 i 的值转成 void* 传过去 (上一讲的方法 2). 修复 2: 用初值为 0 的信号量: 主线程每创建一个线程就 sem_wait 等待, 新线程读完 myid 后 sem_post, 主线程才继续 i++. 这样「读」一定在「改」之前. 互斥锁做不到, 因为互斥锁只能由加锁的线程解锁, 而这里是主线程等、新线程放行; 信号量没有这个限制.

注: 修复 1 中 int 转 void* 再转回 int, 在 64 位系统上编译器会对 (int)vargp 警告指针截断; 上一讲用的是 long, 更干净.

Slide 10

Not all races involve threads — Time of check to time of use (TOCTOU) · ($ rm myfile.txt — between check and use)

if (access("myfile.txt", R_OK) == 0) {        // Check
    FILE *fp = fopen("myfile.txt", "r");      // Use
    while (fgets(fp, buf, sizeof buf) != NULL)
        process_line(buf);
    fclose(fp);
} else {
    fprintf(stderr, "myfile.txt not found\n");
}

Fix: Don't check, just use (but be ready for failure)

FILE *fp = fopen("myfile.txt", "r");
if (fp) {
    while (fgets(fp, buf, sizeof buf) != NULL)
        process_line(buf);
    fclose(fp);
} else {
    fprintf(stderr, "myfile.txt: %s\n", strerror(errno));
}

竞争不一定涉及线程. TOCTOU (检查时刻与使用时刻的竞争): 先用 access 检查文件可读, 再 fopen 使用; 若在两者之间另一个进程删除了文件 (rm myfile.txt), fopen 就会失败, 而代码以为检查过了不会失败, 于是对 NULL 调用 fgets. 在有特权的程序中, 这种空隙还能被攻击者利用 (检查后把文件换成符号链接). 修复: 不要先检查, 直接使用, 并准备好处理失败, 用 strerror(errno) 报告真实的原因.

幻灯片代码错误: 两段代码都写成 fgets(fp, buf, sizeof buf), 参数顺序错了. fgets 的原型是 char *fgets(char *s, int size, FILE *stream), 应为 fgets(buf, sizeof buf, fp).

Races involving signal handlers — Event happens earlier than anticipated

void sigchld_handler(int unused) {
    int status;
    pid_t pid;
    while ((pid = waitpid(-1, &status, WNOHANG|WUNTRACED)) > 0)
        job_status_change(pid, status);
}

void start_fg_job(char **argv) {
    pid_t pid = fork();
    if (pid == -1) {
        perror("fork");
        return;
    } else if (pid == 0) {
        execve(argv[0], argv, environ);
        perror("execve");
        exit(127);
    } else {
        /* ← SIGCHLD delivered */
        add_job(pid, argv);
    }
}

Race Elimination — Don't share state · e.g. use malloc to generate separate copy of argument for each thread · Don't check before using · Attempt to use, see if it failed · Use synchronization primitives · Which synchronization primitive? Depends on the situation

信号处理程序中的竞争: 事件比预期来得早. 父进程 fork 之后、add_job 之前, 子进程可能已经结束, SIGCHLD 到达, 处理程序对一个还不在作业表中的作业调用 job_status_change; 之后 add_job 再把已经结束的作业加进去. 这正是第 17 讲的例子, 修复办法是在 fork 之前阻塞 SIGCHLD.

消除竞争的办法: 不共享状态 (例如为每个线程 malloc 一份参数); 不要先检查再使用, 直接尝试, 看是否失败; 使用同步原语, 用哪种视情况而定.

死锁
Deadlock

Slide 14–15

Deadlock — A program is deadlocked when it is waiting for an event which cannot ever happen · Mathematical impossibility, not just practical · Most common form: · Thread A is waiting for thread B to do something · Thread B is waiting for thread A to do something · Neither can make forward progress

Deadlock caused by wrong locking order

void *thread_1(void *arg) {          void *thread_2(void *arg) {
    pthread_mutex_lock(&mA);             pthread_mutex_lock(&mB);
    pthread_mutex_lock(&mB);             pthread_mutex_lock(&mA);
    // do stuff ...                      // do stuff ...
    pthread_mutex_unlock(&mA);           pthread_mutex_unlock(&mB);
    pthread_mutex_unlock(&mB);           pthread_mutex_unlock(&mA);
}                                    }

死锁: 程序在等待一个不可能发生的事件, 是逻辑上的不可能, 不只是实际上很难. 最常见的形式: A 等 B 做某事, B 等 A 做某事, 谁也无法前进.

加锁顺序不一致导致死锁: 线程 1 先锁 mA 再锁 mB, 线程 2 先锁 mB 再锁 mA. 若线程 1 拿到 mA、线程 2 拿到 mB, 两者都在等对方手里的锁, 永远等下去.

Slide 16

Deadlock Visualized in Progress Graph

Deadlock state: cannot move up or right – both threads are stuck · Any trajectory that enters the deadlock region will eventually reach the deadlock state where each thread is waiting for the other to release a lock · Other trajectories luck out and skirt the deadlock region · Unfortunate fact: trajectory variations may mean deadlock bugs are nondeterministic (don't always manifest, making them hard to debug)

用进度图看死锁: 每把锁产生一个禁止区. 两个禁止区的位置交错, 在它们左下方围出一块死锁区: 轨迹一旦进入, 最终会走到死锁状态, 再也不能向右或向上 (每个方向都撞上禁止区). 其他轨迹运气好, 绕过了死锁区. 麻烦在于: 轨迹随调度变化, 死锁时有时无, 难以调试.

Slide 17

Fix this deadlock with consistent ordering

void *thread_1(void *arg) {
    pthread_mutex_lock(&mA);
    pthread_mutex_lock(&mB);
    // do stuff ...
    pthread_mutex_unlock(&mA);
    pthread_mutex_unlock(&mB);
}

void *thread_2(void *arg) {
    pthread_mutex_lock(&mA);
    pthread_mutex_lock(&mB);
    // do stuff ...
    pthread_mutex_unlock(&mB);
    pthread_mutex_unlock(&mA);
}

Always possible to move up or move right · Inconsistent unlock order does not matter

修复: 所有线程按同一个顺序加锁 (都先 mA 后 mB). 进度图上 a 的禁止区包住了 b 的禁止区, 不再有死锁区, 任何时候都能向上或向右走. 解锁顺序不一致无所谓, 解锁不会阻塞. 一般规则 (互斥锁加锁顺序规则): 给所有互斥锁定一个全序, 每个线程都按这个顺序获取, 程序就不会死锁.

信号量、事件和队列
Semaphores, Events, and Queues

Slide 19–20

Recall: Semaphores — Integer value, always >= 0 (initialize with sem_init) · P(s) operation (aka sem_wait) · If s is zero, wait for a V operation to happen. · Then subtract 1 from s and return. · V(s) operation (aka sem_post) · Add 1 to s. · If there are any threads waiting inside a P operation, resume one of them · Any thread may call P; any thread may call V; no ordering requirements · Key difference from mutexes

Semaphores for Events — Remember this program from Thursday's quiz?

#define N 4
long *pointers[N];

void *thread(void *vargp) {
    long myid = (long) vargp;
    pointers[myid] = &myid;
    sleep(2);
    return NULL;
}

int main(int argc, char *argv[]) {
    long i;
    pthread_t tids[N];

    for (i = 0; i < N; i++)
        Pthread_create(&tids[i], NULL,
                       thread, (void *) i);
    sleep(1);
    for (i = 0; i < N; i++)
        printf("Thread id %u has "
               "local value %ld\n",
               (int) tids[i], *pointers[i]);
    for (i = 0; i < N; i++)
        Pthread_join(tids[i], NULL);
    return 0;
}

Let's fix it. · With semaphores.

回顾信号量: 非负整数; P (sem_wait) 在 s 为 0 时等待, 然后减 1; V (sem_post) 加 1 并唤醒一个等待者. 任何线程都可以 P、任何线程都可以 V, 没有顺序要求, 这是与互斥锁的关键区别, 也是它能表示事件的原因.

上次小测的程序: 每个线程把自己栈上局部变量 myid 的地址存进全局数组 pointers, 然后睡 2 秒; 主线程睡 1 秒后通过这些指针读出各线程的 myid. 它靠 sleep 来「同步»: 指望 1 秒后所有线程都已存好指针, 又指望 2 秒内线程不退出 (退出后栈就失效). 这只是碰运气, 不是真正的同步.

Slide 21

(Semaphores for Events — fixed version)

#define N 4
long *pointers[N];
sem_t ready[N];
sem_t finish;

void *thread(void *vargp) {
    long myid = (long) vargp;
    pointers[myid] = &myid;
    sem_post(&ready[myid]);
    sem_wait(&finish);
    return NULL;
}

int main(int argc, char *argv[]) {
    long i;
    pthread_t tids[N];

    Sem_init(&finish, 0, 0);
    for (i = 0; i < N; i++) {
        Sem_init(&ready[i], 0, 0);
        Pthread_create(&tids[i], NULL,
                       thread, (void *) i);
    }
    for (i = 0; i < N; i++) {
        sem_wait(&ready[i]);
        printf("Thread id %u has "
               "local value %ld\n",
               (int) tids[i], *pointers[i]);
    }
    for (i = 0; i < N; i++)
        sem_post(&finish);
    for (i = 0; i < N; i++)
        Pthread_join(tids[i], NULL);
    return 0;
}

用信号量表示两种事件代替 sleep: ready[i] 表示「线程 i 已经存好指针», finish 表示「主线程已经读完, 线程可以退出». 线程存好指针后 V(ready[myid]), 然后 P(finish) 等待; 主线程对每个 i 先 P(ready[i]) 再读; 全部读完后 V(finish) N 次, 放所有线程退出. 两个信号量初值都是 0 (事件尚未发生). 这样无论调度如何都正确, 也不浪费时间.

Slide 22–23

Queues, Producers, and Consumers — (producer thread → shared queue → consumer thread) · Common synchronization pattern: · Producer waits for empty slot, inserts item in queue, and notifies consumer · Consumer waits for item, removes it from queue, and notifies producer · Examples · Multimedia processing: · Producer creates video frames, consumer renders them · Event-driven graphical user interfaces · Producer detects mouse clicks, mouse movements, and keyboard hits and inserts corresponding events in queue · Consumer retrieves events from queue and paints the display

Producer-Consumer on 1-entry Queue — Maintain two semaphores: full + empty

生产者-消费者是常见的同步模式: 生产者等待空位, 放入一项, 通知消费者; 消费者等待有项, 取出, 通知生产者. 例子: 多媒体处理 (生产者生成视频帧, 消费者渲染); 事件驱动的图形界面 (生产者检测鼠标键盘事件放进队列, 消费者取出事件并重绘屏幕).

只有一个位置的队列用两个信号量: full 表示有几项可取, empty 表示有几个空位. 空时 full = 0、empty = 1; 满时相反. 两者之和始终为 1 (不计操作中间的瞬间).

Slide 24–25

Why 2 Semaphores for 1-entry Queue? — Consider multiple producers & multiple consumers · Producers will contend with each other to get empty · Consumers will contend with each other to get full

/* Producers */                 /* Consumers */
P(&shared.empty);               P(&shared.full);
shared.buf = item;              item = shared.buf;
V(&shared.full);                V(&shared.empty);

Producer-Consumer on n-element Queue — (P1 … Pn — Between 0 and n elements — C1 … Cm) · Requires a mutex and two counting semaphores: · mutex: enforces mutually exclusive access to the queue's innards · slots: counts the available slots in the queue · items: counts the available items in the queue · Makes use of semaphore values > 1 (up to n) · See Fig 12.25 in CSAPP for the code

为什么一个位置要两个信号量? 考虑多个生产者和多个消费者: 生产者之间争夺 empty, 消费者之间争夺 full. 生产者 P(empty) 拿到空位, 写入, V(full) 通知消费者; 消费者 P(full) 拿到一项, 读出, V(empty) 归还空位. 每个信号量只表示一种事件, 一个信号量无法同时表达「可以写」和「可以读».

n 个位置的队列 (教材 12.5.4 的 sbuf 包): 一个互斥锁保护队列内部 (头尾指针); 两个计数信号量: slots 记空位数 (初值 n), items 记项数 (初值 0), 值可以大于 1. 插入: P(slots), 加锁, 放入, 解锁, V(items); 取出: P(items), 加锁, 取出, 解锁, V(slots). 注意先 P 信号量再加锁, 反过来会在队列满或空时拿着锁睡眠, 造成死锁.

读写锁与饥饿
Reader-Writer Locks and Starvation

Slide 27–28

Readers-Writers Problem — (W1 W2 W3: Read/Write Access · R1 R2 R3: Read-only Access) · Problem statement: · Reader threads only read the object · Writer threads modify the object (read/write access) · Writers must have exclusive access to the object · Unlimited number of readers can access the object · Occurs frequently in real systems, e.g., · Online airline reservation system · Multithreaded caching Web proxy

Pthreads Reader/Writer Lock — Data type pthread_rwlock_t · Operations · Acquire read lock: pthread_rwlock_rdlock(pthread_rwlock_t *rwlock) · Acquire write lock: pthread_rwlock_wrlock(pthread_rwlock_t *rwlock) · Release (either) lock: pthread_rwlock_unlock(pthread_rwlock_t *rwlock) · Must be used correctly! · Up to programmer to decide what requires read access and what requires write access

读者-写者问题: 读者线程只读对象, 写者线程修改对象; 写者必须独占访问, 读者可以任意多个同时访问. 真实系统中很常见: 航班订票系统 (大量查询, 少量订票)、多线程缓存 Web 代理 (proxy lab, 多数请求只读缓存).

Pthreads 提供读写锁 pthread_rwlock_t: rdlock 获取读锁 (可与其他读锁共存), wrlock 获取写锁 (独占), unlock 释放. 哪些操作需要读锁、哪些需要写锁, 由程序员判断, 用错了照样有竞争 (例如在读锁下修改了 LRU 链表).

Slide 29–30

Reader/Writer Starvation — Thread 1 has a read lock. Thread 2 is waiting for a write lock. Thread 3 tries to take a read lock. What happens?

Option 1: R2 gets read lock immediately · Endless stream of overlapping readers → W waits forever · Option 2: Writer always gets lock as soon as possible · Endless stream of overlapping writers → readers wait forever (not shown)

Starvation — A thread is starved when it makes no forward progress for an unacceptably long time · Unlike deadlock, it's possible for it to get unstuck eventually · “Unacceptably long” depends on the application · Algorithms that guarantee no starvation are called fair · Fair R/W locks: every waiter receives the lock in first-come first-served order (several readers can receive the lock at the same time) · Fairness is more complicated to implement · Fairness can mean all threads are slower than they would be in an unfair system (e.g. “lock convoy problem”)

读写锁的饥饿: 读者 1 持有读锁, 写者在等, 读者 2 来了. 选项 1 (读者优先): 让读者 2 立即进入, 只要读者源源不断地重叠, 写者就永远等下去. 选项 2 (写者优先): 写者一来就优先, 写者源源不断时读者永远等.

饥饿: 一个线程在不可接受的长时间里没有进展. 与死锁不同, 它最终可能解脱; 多长算「不可接受」取决于应用. 保证不会饥饿的算法叫公平的: 公平的读写锁按先来先服务的顺序授予锁 (相邻的多个读者可以同时获得). 公平实现更复杂, 而且可能让所有线程都比不公平时慢 (「锁护航」问题: 锁按顺序交接, 每次都要等下一个线程被唤醒调度, 整体吞吐下降).

线程安全的 API 设计
Thread-Safe API Design

Slide 33–34

Thread-Safe APIs — A function is thread-safe if it always produces correct results when called repeatedly from multiple concurrent threads. · Reasons for a function not to be thread-safe: · 1. Internal shared state, no locking (e.g. your malloc) · 2. Internal state modified across multiple uses (e.g. rand) · 3. Returns a pointer to a static variable (e.g. strtok) · 4. Calls a function that does any of the above

Thread-Unsafe Functions (Class 1) — These functions would be thread-safe if they began with pthread_mutex_lock(&l) and ended with pthread_mutex_unlock(&l) for some lock L · Good example: malloc, realloc, free · Your implementation will crash if called from multiple concurrent threads · The C library's implementation won't; it has internal locks · Locking slows things down, of course

一个函数是线程安全的, 当且仅当被多个并发线程反复调用时总能给出正确结果. 线程不安全的四类原因: ① 有内部共享状态却不加锁 (例如你在 malloc lab 写的 malloc); ② 内部状态跨多次调用保持 (rand); ③ 返回指向静态变量的指针 (strtok); ④ 调用了前三类函数.

第 1 类: 只要在函数开头加锁、结尾解锁就变成线程安全的. 例如 malloc、realloc、free: 你自己的实现被多线程同时调用会崩溃, C 库的实现有内部锁所以不会. 代价是加锁变慢.

Slide 35–36

Thread-Unsafe Functions (Class 2) — Relying on persistent state across multiple function invocations · Example: Random number generator that relies on static state

static unsigned int next = 1;

/* rand: return pseudo-random integer on 0..32767 */
int rand(void) {
    next = next*1103515245 + 12345;
    return (unsigned int)(next/65536) % 32768;
}

/* srand: set seed for rand() */
void srand(unsigned int seed) {
    next = seed;
}

Difference from class 1: locking would not fix the problem · 2 threads call rand() simultaneously, both get different results than if only one made a sequence of calls to rand()

Fixing Class 2 Thread-Unsafe Functions — Pass state as part of argument · and, thereby, eliminate static state

/* rand_r - return pseudo-random integer on 0..32767 */
int rand_r(int *nextp)
{
    *nextp = *nextp*1103515245 + 12345;
    return (unsigned int)(*nextp/65536) % 32768;
}

Requires API change · Callers responsible for allocating space for state

第 2 类: 依赖跨调用的持久状态. rand 是线性同余生成器, 下一个数由静态变量 next 算出. 与第 1 类不同, 加锁也没用: 即使每次调用都是原子的, 两个线程交替调用 rand, 各自得到的序列也与单线程连续调用时不同 (一个线程想用固定种子复现序列就做不到). 修复: 把状态作为参数传进来, 消除静态状态, 即 rand_r(nextp). 这要改 API, 调用者负责为状态分配空间, 每个线程各用自己的一份.

幻灯片小错: rand_r 的参数写成 int *nextp, 而 rand 中的状态是 unsigned int. 用有符号 int 时 *nextp*1103515245 会发生有符号溢出, 在 C 中是未定义行为, 而且 *nextp/65536 对负数的结果也不同. 应为 unsigned int *nextp (教材图 12.39 与 POSIX 的 rand_r 都是 unsigned int *).

Slide 37–38

Thread-Unsafe Functions (Class 3) — Returning a pointer to a static variable · Like class 2, locking inside function would not help · Race between use of result and calls from another thread · Fix: make caller supply space for result · Requires API change (also like class 2) · Can be awkward for caller: how much space is required?

/* Convert integer to string */
char *itoa(int x)
{
    static char buf[11];
    snprintf(buf, 11, "%d", x);
    return buf;
}

/* Convert integer to string (thread-safe) */
void itoa_r(int x, char *buf, size_t bufsz)
{
    snprintf(buf, bufsz, "%d", x);
}

Thread-Unsafe Functions (Class 4) — Calling thread-unsafe functions · Any function that uses a class 1, 2, or 3 function internally is just as thread-unsafe as that function itself · This applies transitively · Only fix is to modify the function to use only thread-safe functions · This may or may not involve API changes

第 3 类: 返回指向静态变量的指针. 所有调用共用同一个 buf, 线程 A 拿到指针还没用完, 线程 B 的调用就把内容改了. 函数内部加锁也没用, 竞争发生在调用者使用结果的时候. 修复: 让调用者提供存放结果的空间 (itoa_r), 同样要改 API, 而且调用者不一定知道该准备多大. (另一种不改 API 的办法是「加锁并复制»: 写一个包装函数, 加锁后调用原函数, 把结果复制到调用者的缓冲区再解锁.)

第 4 类: 调用了第 1–3 类函数的函数同样不安全, 而且具有传递性. 唯一的修复是改成只调用线程安全的函数, 可能需要也可能不需要改 API.

幻灯片小错: static char buf[11] 对 32 位 int 不够大: 最小值 −2147483648 有 11 个字符, 加上结尾的 '\0' 需要 12 字节. snprintf(buf, 11, …) 不会越界, 但会把结果截断成 "-214748364", 返回错误的字符串. 应为 buf[12].

ISO C 标准库的大多数函数是线程安全的 (malloc、free、printf、scanf), 例外有 strtok、rand、asctime 等. 很多老的 Unix 库函数不安全, 通常有安全的替代: 时间函数用 strftime (或 asctime_r、localtime_r), gethostbyname/gethostbyaddr/inet_ntoa 用第 20 讲的 getaddrinfo/getnameinfo, rand 用 rand_r. 注意 C 库的随机数生成器都很老、很弱, 安全用途要用现代的密码学安全随机数生成器 (CSPRNG).

可重入函数: 被多个线程调用时不访问任何共享变量. 它是线程安全函数的一个重要子集, 不需要任何同步操作, 因而高效. 第 2 类函数要变得线程安全, 唯一的办法就是改成可重入的 (rand_r).

Slide 41–42

Threads / Signals Interactions — (I_curr: fprintf.lock() → Receive signal → Handler → I_next: fprintf.unlock()) · Many library functions use lock-and-copy for thread safety · malloc · Free lists · fprintf, printf, puts · So that outputs from multiple threads don't interleave · snprintf · Calls malloc internally for scratch space · OK to interrupt them with locks held · … as long as the handler doesn't use them itself!

Bad Thread / Signal Interactions — (fprintf.lock() → signal → handler calls fprintf.lock() …) · What if: · Signal received while library function holds lock · Handler calls same (or related) library function · Deadlock! · Signal handler cannot proceed until it gets lock · Main program cannot proceed until handler completes · Key Point · Threads employ symmetric concurrency · Signal handling is asymmetric

线程安全与信号的相互作用: 很多库函数靠内部加锁实现线程安全, 例如 malloc (保护空闲链表)、fprintf/printf/puts (保证多个线程的输出不交错)、snprintf (内部会调用 malloc 申请临时空间). 在它们持有锁时被信号打断没关系, 只要处理程序自己不调用它们.

若处理程序调用了同一个 (或相关的) 库函数, 就死锁: 处理程序拿不到锁无法继续, 主程序要等处理程序结束才能释放锁 (第 21 讲 printf 卡死的例子). 关键: 线程之间的并发是对称的, 一个线程等锁时持锁线程照样能运行; 信号处理是不对称的, 处理程序不返回, 被打断的主程序就无法运行. 所以线程安全不等于异步信号安全.
