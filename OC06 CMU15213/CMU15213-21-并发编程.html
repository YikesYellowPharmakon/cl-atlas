Concurrent Programming is Hard! — The human mind tends to be sequential · The notion of time is often misleading · Thinking about all possible sequences of events in a computer system is at least error prone and frequently impossible · Classical problem classes of concurrent programs: · Races: outcome depends on arbitrary scheduling decisions elsewhere in the system · Deadlock: improper resource allocation prevents forward progress · Livelock / Starvation / Fairness: external events and/or system scheduling decisions can prevent sub-task progress

Data Race

/* Global shared variable */
volatile long cnt = 0; /* Counter */

void *thread(void *vargp)
{
    long i, niters =
        *((long *)vargp);

    for (i = 0; i < niters; i++)
        cnt++;

    return NULL;
}

本讲: 并发编程基础, 以及写并发服务器的三种方法: 基于进程、基于事件、基于线程 (教材 12.1–12.3).

并发编程难: 人的思维习惯是顺序的; 「时间」的直觉常常误导人; 要考虑系统中所有可能的事件顺序, 很容易出错, 往往根本做不到. 并发程序的经典问题: 竞争 (结果取决于系统别处的任意调度决定)、死锁 (资源分配不当, 谁也无法前进)、活锁 / 饥饿 / 公平性 (外部事件或调度使某些子任务无法前进).

数据竞争的例子: 多个线程各自把全局计数器 cnt 加 niters 次. cnt++ 实际是「读、加、写」三步, 两个线程的这三步交错时, 一次加法会被另一次覆盖, 最终结果常常小于预期. volatile 只保证每次都访问内存, 不能使 ++ 成为原子操作. 详见下一讲.

Deadlock — (photo of a gridlocked traffic intersection)

Example from signal handlers. · Why don't we use printf in handlers?

void catch_child(int signo) {
    printf("Child exited!\n"); // this call may reenter printf/puts! BAD! DEADLOCK!
    while (waitpid(-1, NULL, WNOHANG) > 0) continue; // reap all children
}

Printf code: · Acquire lock · Do something · Release lock · (I_curr: Acquire lock → Receive signal → (Try to) acquire lock → Deadlocked!) · What if signal handler interrupts call to printf?

死锁, 像十字路口四个方向的车互相堵死. 信号处理程序中的例子 (第 17 讲说过处理程序里不能用 printf, 这里讲原因): printf 内部先获取一把锁, 做事, 再释放锁. 如果主程序正在 printf 里、已经拿到锁, 这时信号到来, 处理程序也调用 printf, 它要等这把锁, 而锁的持有者 (被打断的主程序) 要等处理程序返回才能继续: 互相等待, 永远卡住.

Why Does Printf require Locks? — Printf (and fprintf, sprintf) implement buffered I/O · (Buffered Portion: no longer in buffer | already read | unread | unseen — Current File Position) · Require locks to access the shared buffers

用 gdb 附到卡住的进程上看调用栈, 从下往上读: main 调用 printf (#7、#6), 正在 printf 内部时信号处理程序被调用 (#5), sigchld 又调用 printf (#3), 最后卡在等待锁 (#0 __lll_lock_wait_private). 正好印证了上面的分析.

printf 为什么要锁? 它实现了带缓冲的 I/O (第 18 讲), stdout 的缓冲区是共享的, 多个线程同时写必须加锁, 否则缓冲区会被破坏. 锁防得了别的线程, 却防不了同一线程里被信号打断后的重入.

活锁: 各方都在不停地动, 却谁也前进不了, 像在环岛里一圈圈绕却出不去 (例如两个人在走廊里同时向同一侧让路, 反复如此). 饥饿: 黄车必须给绿车让路, 而绿车源源不断, 整个系统在前进, 但某个个体无限期等待.

总结三类问题的日常比喻: 死锁像交通大堵塞; 活锁/饥饿像排队时总有人插到你前面; 竞争像谁抢到飞机上最后一个座位. 很多内容超出本课范围, 后几讲会讲一部分. 并发虽难, 但很有用, 而且 (在多核时代) 越来越必要.

迭代服务器的缺陷
Iterative Servers

Slide 19–22

Reminder: Iterative Echo Server (client: socket, connect, rio_writen, rio_readlineb, close · server: socket, bind, listen, accept, rio_readlineb, rio_writen, rio_readlineb (EOF), close; await connection request from next client)

Iterative Servers — Iterative servers process one request at a time · (Client 1: connect, write, call read, ret read, close · Server: accept, read, write, read, close · Client 2: connect, then waits for server to finish with Client 1; accept; write; ret read)

Where Does Second Client Block? — Second client attempts to connect to iterative server · Call to connect returns · Even though connection not yet accepted · Server side TCP manager queues request · Feature known as “TCP listen backlog” · Call to rio_writen returns · Server side TCP manager buffers input data · Call to rio_readlineb blocks · Server hasn't written anything for it to read yet.

迭代服务器一次只处理一个客户: 服务完客户 1、关闭连接, 才回到 accept 接受客户 2. 客户 2 在哪里阻塞? 不是 connect: 服务器端的 TCP 已经把连接请求放进队列 (就是 listen 的 backlog), connect 即可返回; rio_writen 也会返回, 数据被服务器端内核缓冲; 直到 rio_readlineb 才阻塞, 因为服务器还没给它写任何东西.

Slide 23–24

Fundamental Flaw of Iterative Servers

Solution: use concurrent servers instead · Concurrent servers use multiple concurrent flows to serve multiple clients at the same time

Approaches for Writing Concurrent Servers — Allow server to handle multiple clients concurrently · 1. Process-based · Kernel automatically interleaves multiple logical flows · Each flow has its own private address space · 2. Event-based · Programmer manually interleaves multiple logical flows · All flows share the same address space · Uses technique called I/O multiplexing · 3. Thread-based · Kernel automatically interleaves multiple logical flows · Each flow shares the same address space · Hybrid of process-based and event-based

根本缺陷: 客户 1 连上后, 用户「出去吃午饭」不输入, 服务器就一直阻塞在读客户 1 上, 客户 2 只能干等. 一个慢客户就能让所有人停摆. 解决办法: 并发服务器, 用多个并发流同时服务多个客户.

三种写法: ① 基于进程: 内核自动交错多个逻辑流, 每个流有私有地址空间; ② 基于事件: 程序员手动交错多个逻辑流, 所有流共享一个地址空间, 用 I/O 多路复用技术; ③ 基于线程: 内核自动交错, 所有流共享地址空间, 是前两者的混合.

基于进程的服务器
Process-based Servers

Slide 27–28

Approach #1: Process-based Servers — Spawn separate process for each client

基于进程的服务器: 每接受一个客户, 就 fork 一个子进程专门服务它, 父进程立刻回到 accept. 客户 1 的用户再慢, 也只阻塞子进程 1, 客户 2 由子进程 2 服务, 互不影响.

Slide 29–35

Iterative Echo Server — Accept a connection request · Handle echo requests until client terminates

Making a Concurrent Echo Server · Why? · Process-Based Concurrent Echo Server

int main(int argc, char **argv)
{
    int listenfd, connfd;
    socklen_t clientlen;
    struct sockaddr_storage clientaddr;

    Signal(SIGCHLD, sigchld_handler);
    listenfd = Open_listenfd(argv[1]);
    while (1) {
        clientlen = sizeof(struct sockaddr_storage);
        connfd = Accept(listenfd, (SA *) &clientaddr, &clientlen);
        if (Fork() == 0) {
            Close(listenfd); /* Child closes its listening socket */
            echo(connfd);    /* Child services client */
            Close(connfd);   /* Child closes connection with client */
            exit(0);         /* Child exits */
        }
        Close(connfd); /* Parent closes connected socket (important!) */
    }
}
void sigchld_handler(int sig)
{
    while (waitpid(-1, 0, WNOHANG) > 0)
        ;
    return;
}

Reap all zombie children

从迭代 echo 服务器改成并发版本 (第 29–34 页逐步改写): accept 之后 fork; 子进程关闭不需要的监听描述符, 调用 echo 服务客户, 关闭连接后退出; 父进程关闭自己那份 connfd (注释强调 important!), 回到 accept. 再安装 SIGCHLD 处理程序回收子进程: 用 WNOHANG 循环 waitpid, 一次回收所有已结束的子进程 (信号不排队, 第 17 讲).

第 32 页问「为什么父进程要关 connfd»: fork 后 connfd 指向的打开文件表项 refcnt 为 2, 父进程不关, 子进程关闭后 refcnt 仍为 1, 连接永远不会真正关闭, 客户等不到 EOF; 而且父进程的描述符会越积越多, 最终耗尽.

与第 17 讲的准则不一致: 这里的 sigchld_handler 调用了 waitpid, 却没有按准则 G2 保存和恢复 errno (waitpid 最后一次返回 −1 时会把 errno 设为 ECHILD, 可能覆盖主程序正要检查的 errno). 教材图 12.5 也是这样写的; 严格的写法应在开头 int olderrno = errno;, 结尾 errno = olderrno;.

Slide 36–39

Recall: Concurrent Server accept — 1. Server blocks in accept, waiting for connection request on listening descriptor listenfd(3) · 2. Client makes connection request by calling connect · 3. Server returns connfd from accept. Forks child to handle client. Connection is now established between clientfd and connfd(4)

Process-based Server Execution Model — (Listening server process receives connection requests; Client 1 server process and Client 2 server process exchange data with their clients) · Each client handled by independent child process · No shared state between them · Both parent & child have copies of listenfd and connfd · Parent must close connfd · Child should close listenfd

Issues with Process-based Servers — Listening server process must reap zombie children · to avoid fatal memory leak · Parent process must close its copy of connfd · Kernel keeps reference count for each socket/open file · After fork, refcnt(connfd) = 2 · Connection will not be closed until refcnt(connfd) = 0

Pros and Cons of Process-based Servers — + Handle multiple connections concurrently. · + Clean sharing model. · descriptors (no) · file tables (yes) · global variables (no) · + Simple and straightforward. · – Additional overhead for process control. · – Nontrivial to share data between processes. · (This example too simple to demonstrate)

执行模型: 监听进程只负责接受连接, 每个客户由独立的子进程处理, 子进程之间没有共享状态. fork 后父子都有 listenfd (3) 和 connfd (4) 的副本, 父进程必须关 connfd, 子进程应该关 listenfd.

要注意的问题: 必须回收僵尸子进程, 否则内存泄漏; 父进程必须关闭自己的 connfd, 因为内核为每个打开的文件 (包括套接字) 维护引用计数, refcnt 降到 0 连接才关闭.

优点: 能同时处理多个连接; 共享模型清晰: 描述符不共享 (各有一份描述符表), 打开文件表共享, 全局变量不共享; 简单直接. 缺点: 进程控制的开销大; 进程之间共享数据不容易 (要用管道、共享内存等进程间通信机制).

基于事件的服务器
Event-based Servers

Slide 41–43

Approach #2: Event-based Servers — Server maintains set of active connections · Array of connfd's · Repeat: · Determine which descriptors (connfd's or listenfd) have pending inputs · e.g., using select function · arrival of pending input is an event · If listenfd has input, then accept connection · and add new connfd to array · Service all connfd's with pending inputs · Details for select-based server in book

Pros and Cons of Event-based Servers — + One logical control flow and address space. · + Can single-step with a debugger. · + No process or thread control overhead. · Design of choice for high-performance Web servers and search engines. e.g., Node.js, nginx, Tornado · – Significantly more complex to code than process-based or thread-based designs. · – Hard to provide fine-grained concurrency. · E.g., how to deal with partial HTTP request headers · – Cannot take advantage of multi-core. · Single thread of control

基于事件的服务器只有一个进程、一个线程, 维护一组活动连接 (connfd 数组), 反复执行: 用 select (或 poll、epoll) 一次性询问「哪些描述符有待处理的输入», 输入到达就是一个事件; listenfd 有输入就 accept, 把新的 connfd 加入数组; 对每个有输入的 connfd 读一行并回显. 每个客户的处理进度要显式保存成状态 (状态机), 由程序员自己在各客户之间切换.

优点: 只有一个逻辑流和地址空间, 可以用调试器单步; 没有进程、线程控制的开销, 是高性能 Web 服务器和搜索引擎的首选 (Node.js、nginx、Tornado). 缺点: 比另外两种难写得多; 难以做细粒度的并发, 例如一个客户只发来半行 HTTP 头部, 若用 rio_readlineb 等整行就会把整个服务器堵住; 只有一个控制流, 不能利用多核.

线程
Thread-based Servers

Slide 45–47

Approach #3: Thread-based Servers — Very similar to approach #1 (process-based) · …but using threads instead of processes

Traditional View of a Process — Process = process context + code, data, and stack · Process context: Program context: Data registers · Condition codes · Stack pointer (SP) · Program counter (PC) · Kernel context: VM structures · Descriptor table · brk pointer · Code, data, and stack: Stack · Shared libraries · Run-time heap · Read/write data · Read-only code/data

Alternate View of a Process — Process = thread + code, data, and kernel context · Thread (main thread): Stack · Thread context: Data registers · Condition codes · Stack pointer (SP) · Program counter (PC) · Code, data, and kernel context: Shared libraries · Run-time heap · Read/write data · Read-only code/data · Kernel context: VM structures · Descriptor table · brk pointer

基于线程的服务器和基于进程的很像, 只是用线程代替进程. 先换个角度看进程: 传统看法是「进程 = 进程上下文 + 代码、数据和栈», 上下文分程序上下文 (寄存器、条件码、栈指针、程序计数器) 和内核上下文 (虚拟内存结构、描述符表、brk 指针). 另一种看法: 「进程 = 线程 + 代码、数据和内核上下文», 线程由栈和线程上下文 (寄存器、条件码、SP、PC) 组成. 普通进程只有一个线程, 叫主线程.

Slide 48–49

A Process With Multiple Threads — Multiple threads can be associated with a process · Each thread has its own logical control flow · Each thread shares the same code, data, and kernel context · Each thread has its own stack for local variables · but not protected from other threads · Each thread has its own thread id (TID)

Logical View of Threads — Threads associated with process form a pool of peers · Unlike processes which form a tree hierarchy

一个进程可以有多个线程: 每个线程有自己的逻辑控制流、自己的栈 (放局部变量) 和线程 ID; 所有线程共享代码、数据 (全局变量、堆) 和内核上下文 (包括描述符表). 注意: 每个线程的栈并不受保护, 别的线程只要拿到指针就能读写它.

一个进程的线程组成一个对等的池, 没有父子关系 (主线程只是第一个运行的线程), 任何线程都可以 join 或杀死别的线程; 而进程组成树形层次.

Slide 50–52

Concurrent Threads — Two threads are concurrent if their flows overlap in time · Otherwise, they are sequential · Examples: · Concurrent: A & B, A&C · Sequential: B & C

Concurrent Thread Execution — Single Core Processor · Simulate parallelism by time slicing · Multi-Core Processor · Can have true parallelism

Threads vs. Processes — How threads and processes are similar · Each has its own logical control flow · Each can run concurrently with others (possibly on different cores) · Each is context switched · How threads and processes are different · Threads share all code and data (except local stacks) · Processes (typically) do not · Threads are somewhat less expensive than processes · Process control (creating and reaping) twice as expensive as thread control · Linux numbers: · ~20K cycles to create and reap a process · ~10K cycles (or less) to create and reap a thread

线程的并发定义与进程相同 (第 16 讲): 时间上重叠就是并发. 单核处理器靠时间片轮转模拟并行; 多核处理器可以真正并行.

线程与进程相同之处: 各有逻辑控制流, 可以并发运行 (可能在不同核上), 都要上下文切换. 不同之处: 线程共享全部代码和数据 (除了各自的栈), 进程一般不共享; 线程更便宜, 在 Linux 上创建并回收一个进程约 2 万个周期, 线程约 1 万个或更少 (线程切换也不用换页表).

Slide 55–57

The Pthreads "hello, world" Program

/*
 * hello.c - Pthreads "hello, world" program
 */
#include "csapp.h"
void *thread(void *vargp);

int main(int argc, char** argv)
{
    pthread_t tid;
    Pthread_create(&tid, NULL, thread, NULL);
    Pthread_join(tid, NULL);
    return 0;
}

void *thread(void *vargp) /* thread routine */
{
    printf("Hello, world!\n");
    return NULL;
}

(Annotations on Pthread_create: Thread ID · Thread attributes (usually NULL) · Thread routine · Thread arguments (void *p) · on Pthread_join: Return value (void **p))

Execution of Threaded “hello, world” — Main thread: call Pthread_create() → Pthread_create() returns → call Pthread_join() → Main thread waits for peer thread to terminate → Pthread_join() returns → exit() Terminates main thread and any peer threads · Peer thread: printf() → return NULL; Peer thread terminates

Or, … — Main thread doesn't need to wait for peer thread to terminate · And many many more possible ways for this code to execute.

Pthreads 版 hello world: pthread_create 的四个参数依次是: 存放新线程 ID 的地址、线程属性 (通常 NULL)、线程函数、传给线程函数的参数. 线程函数的类型固定为 void *f(void *), 参数和返回值都是通用指针, 要传多个值就打包成结构体. pthread_join 等待指定线程结束, 第二个参数 (void **) 接收它的返回值.

执行过程: 主线程创建对等线程后调用 join 等待; 对等线程打印后返回; join 返回, 主线程 exit, 这会终止进程中所有线程. 第 57 页: 执行顺序也可能是对等线程先运行完, 主线程到 join 时直接返回, 还有很多别的交错方式. 若主线程不 join 就直接 return, 对等线程可能来不及打印就被终止.

Slide 58–59

Thread-Based Concurrent Echo Server

int main(int argc, char **argv)
{
    int listenfd, *connfdp;
    socklen_t clientlen;
    struct sockaddr_storage clientaddr;
    pthread_t tid;

    listenfd = Open_listenfd(argv[1]);
    while (1) {
        clientlen=sizeof(struct sockaddr_storage);
        connfdp = Malloc(sizeof(int));
        *connfdp = Accept(listenfd, (SA *) &clientaddr, &clientlen);
        Pthread_create(&tid, NULL, thread, connfdp);
    }
    return 0;
}

Spawn new thread for each client · Pass it copy of connection file descriptor · Note use of Malloc()! [but not Free()]

Thread-Based Concurrent Server (cont)

/* Thread routine */
void *thread(void *vargp)
{
    int connfd = *((int *)vargp);
    Pthread_detach(pthread_self());
    Free(vargp);
    echo(connfd);
    Close(connfd);
    return NULL;
}

Run thread in “detached” mode. · Runs independently of other threads · Reaped automatically (by kernel) when it terminates · Free storage allocated to hold connfd · Close connfd (important!)

基于线程的 echo 服务器: 每接受一个连接就创建一个线程服务它. 主线程把 connfd 放进 malloc 来的一小块内存, 把指针传给线程 (为什么不直接传 &connfd, 见下文); 主线程不 free, 由线程负责释放.

线程函数: 先把描述符取到自己的局部变量里; pthread_detach(pthread_self()) 把自己设为分离状态, 独立运行, 结束时由系统自动回收资源; free 掉参数内存; 服务客户; 关闭 connfd. 这里关闭很重要: 线程共享描述符表, connfd 只有一份 (不像进程版父子各一份), 不关就泄漏.

Slide 60–61

Thread-based Server Execution Model — (Listening server main thread receives connection requests; Client 1 server peer thread and Client 2 server peer thread exchange data with their clients) · Each client handled by individual peer thread · Threads share all process state except TID · Each thread has a separate stack for local variables

Issues With Thread-Based Servers — Must run “detached” to avoid memory leak · At any point in time, a thread is either joinable or detached · Joinable thread can be reaped and killed by other threads · must be reaped (with pthread_join) to free memory resources · Detached thread cannot be reaped or killed by other threads · resources are automatically reaped on termination · Default state is joinable · use pthread_detach(pthread_self()) to make detached · Must be careful to avoid unintended sharing · For example, passing pointer to main thread's stack · Pthread_create(&tid, NULL, thread, (void *)&connfd); · All functions called by a thread must be thread-safe · (next lecture)

执行模型: 主线程监听, 每个客户由一个对等线程处理; 线程共享除线程 ID 以外的全部进程状态 (各自的栈只是逻辑上分开).

要注意: ① 必须分离运行以免内存泄漏. 线程要么是可结合的 (joinable, 默认), 可以被其他线程回收或杀死, 必须有人 pthread_join 才释放资源; 要么是分离的 (detached), 不能被回收或杀死, 结束时资源自动释放. 服务器的主线程不会去 join 每个线程, 所以线程要自己分离. ② 小心无意的共享, 例如把主线程栈上变量的地址传给线程. ③ 线程调用的所有函数都必须是线程安全的 (下一讲).

No Race · Single core laptop: For each “0” there is some later “2” here · Multicore server: And here, values are all over the place: Some bins get 0, some get 2 or more

Producer-Consumer Model · Allocate in main · Free in thread routine

Pros and Cons of Thread-Based Designs — + Easy to share data structures between threads · e.g., logging information, file cache · + Threads are more efficient than processes · – Unintentional sharing can introduce subtle and hard-to-reproduce errors! · The ease with which data can be shared is both the greatest strength and the greatest weakness of threads · Hard to know which data shared & which private · Hard to detect by testing · Probability of bad race outcome often very low · But nonzero! · Future lectures

Summary: Approaches to Concurrency — Process-based · Hard to share resources: Easy to avoid unintended sharing · High overhead in adding/removing clients · Event-based · Tedious and low level · Total control over scheduling · Very low overhead · Cannot create as fine grained a level of concurrency · Does not make use of multi-core · Thread-based · Easy to share resources: Perhaps too easy ☺ · Medium overhead · Not much control over scheduling policies · Difficult to debug: Event orderings not repeatable

正确的传参方式: 每个线程一块独立的内存, 主线程 malloc 并写入 (生产者), 线程读出后 free (消费者). 这样每个线程拿到的指针各不相同, 没有竞争.

线程方案的优点: 线程之间很容易共享数据结构 (如日志、文件缓存); 比进程高效. 缺点: 无意的共享会引入微妙、难以重现的错误. 容易共享既是线程最大的长处, 也是最大的弱点: 很难知道哪些数据是共享的、哪些是私有的; 测试很难发现, 坏结果的概率往往很低, 但不为零.
