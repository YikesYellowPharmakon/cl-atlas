Today — Basic concepts · Implicit free lists

Dynamic Memory Allocation — Programmers use dynamic memory allocators (such as malloc) to acquire virtual memory (VM) at runtime · For data structures whose size is only known at runtime · Dynamic memory allocators manage an area of process VM known as the heap · (Application → Dynamic Memory Allocator → Heap; process layout: Kernel virtual memory, User stack (%rsp), Memory-mapped region for shared libraries, “The break”, Run-time heap (created by malloc), Read/write segment (.data, .bss), Read-only segment (.init, .text, .rodata) at 0x400000, Unused)

  • Allocator maintains heap as collection of variable sized blocks, which are either allocated or free
  • Types of allocators · Explicit allocator: application allocates and frees space · e.g., malloc and free in C · Implicit allocator: application allocates, but does not free space · e.g., new and garbage collection in Java
  • Will discuss simple explicit memory allocation today

本讲和下一讲讲动态内存分配, 也就是 malloclab 要实现的东西. 程序在运行时才知道需要多大的数据结构时, 用 malloc 这类动态内存分配器向系统要虚拟内存. 分配器管理进程地址空间中的一块区域: 堆, 它在数据区之上, 顶端叫 break (brk), 向高地址增长.

分配器把堆看成一组大小不一的块, 每块要么已分配, 要么空闲. 两类分配器: 显式分配器, 程序自己申请也自己释放 (C 的 malloc/free); 隐式分配器, 程序只申请, 不再用的块由分配器自动回收, 即垃圾回收 (Java 的 new). 本讲讲简单的显式分配.

Slide 6–7

The malloc Package

#include <stdlib.h>

void *malloc(size_t size)
  • Successful: · Returns a pointer to a memory block of at least size bytes aligned to a 16-byte boundary (on x86-64) · If size == 0, returns NULL
  • Unsuccessful: returns NULL (0) and sets errno
void free(void *p)
  • Returns the block pointed at by p to pool of available memory
  • p must come from a previous call to malloc, calloc, or realloc

Other functions · calloc: Version of malloc that initializes allocated block to zero · realloc: Changes the size of a previously allocated block · sbrk: Used internally by allocators to grow or shrink the heap

malloc Example

#include <stdio.h>

void foo(long n) {
    long i, *p;

    /* Allocate a block of n longs */
    p = (long *) malloc(n * sizeof(long));
    if (p == NULL) {
        perror("malloc");
        exit(0);
    }

    /* Initialize allocated block */
    for (i=0; i<n; i++)
        p[i] = i;

    /* Do something with p */
    . . .

    /* Return allocated block to the heap */
    free(p);
}

malloc(size) 成功时返回一块至少 size 字节的内存, 在 x86-64 上按 16 字节对齐 (能存放任何类型); 失败返回 NULL 并设置 errno. free(p) 把块还给分配器, p 必须是之前 malloc、calloc 或 realloc 返回的指针. calloc 分配并清零, realloc 改变已分配块的大小 (可能搬到新位置), sbrk 是分配器内部用来扩大或缩小堆的系统调用.

例子: 分配 n 个 long, 先检查是否返回 NULL (用 perror 打印出错原因), 使用完后 free.

幻灯片小错: "If size == 0, returns NULL" 不准确. C 标准规定 malloc(0) 的结果由实现决定, 可以返回 NULL, 也可以返回一个不能解引用、但可以传给 free 的唯一指针; glibc 返回的是后者. 另外例子用到 malloc 和 exit 却只包含了 <stdio.h>, 应包含 <stdlib.h>; 出错时 exit(0) 表示成功退出, 一般应写 exit(1).

Slide 10

Constraints

  • Applications · Can issue arbitrary sequence of malloc and free requests · free request must be to a malloc'd block
  • Explicit Allocators · Can't control number or size of allocated blocks · Must respond immediately to malloc requests · i.e., can't reorder or buffer requests · Must allocate blocks from free memory · i.e., can only place allocated blocks in free memory · Must align blocks so they satisfy all alignment requirements · 16-byte (x86-64) alignment on 64-bit systems · Can manipulate and modify only free memory · Can't move the allocated blocks once they are malloc'd · i.e., compaction is not allowed. Why not?

约束. 程序可以发出任意顺序的 malloc 和 free (free 的必须是已分配的块). 显式分配器则受到诸多限制: 不能决定块的数量和大小; 必须立即响应每个请求, 不能重排或攒起来一起处理; 只能在空闲内存中分配; 必须满足对齐 (x86-64 上 16 字节); 只能修改空闲内存; 已分配的块不能移动, 即不允许压缩 (compaction). 原因: C 程序手里拿着指向这些块的裸指针 (可能存在任何地方, 甚至被转成整数), 分配器无法找到并更新它们; 有垃圾回收的语言能精确知道所有指针, 才能做压缩.

Slide 11–12

Performance Goal: Throughput — Given some sequence of malloc and free requests: R0​,R1​,…,Rk​,…,Rn−1​ · Goals: maximize throughput and peak memory utilization · These goals are often conflicting · Throughput: · Number of completed requests per unit time · Example: · 5,000 malloc calls and 5,000 free calls in 10 seconds · Throughput is 1,000 operations/second

Performance Goal: Minimize Overhead — After k requests we have: · Def: Aggregate payload Pk​ · malloc(p) results in a block with a payload of p bytes · The aggregate payload Pk​ is the sum of currently allocated payloads · The peak aggregate payload maxi≤k​Pi​ is the maximum aggregate payload at any point in the sequence up to request · Def: Current heap size Hk​ · Assume heap only grows when allocator uses sbrk, never shrinks · Def: Overhead, Ok​ · Fraction of heap space NOT used for program data · Ok​=(Hk​/maxi≤k​Pi​)−1.0

分配器的两个性能目标, 而且往往相互冲突: ① 吞吐量, 单位时间完成的请求数 (10 秒内 5000 次 malloc + 5000 次 free, 吞吐量 1000 次/秒); ② 内存利用率高, 即开销小.

定义: 有效载荷 (payload) 是程序请求的字节数; 第 k 个请求后的聚合有效载荷 P_k 是当前所有已分配块的有效载荷之和; 堆大小 H_k (假设堆只增不减). 开销 O_k = H_k / (到目前为止 P 的最大值) − 1, 即堆中没用于程序数据的比例. 例如峰值载荷 100 KB 而堆长到 110 KB, 开销 10%.

Fragmentation — Poor memory utilization caused by fragmentation · Internal fragmentation · External fragmentation

Internal Fragmentation — For a given block, internal fragmentation occurs if payload is smaller than block size · Caused by · Overhead of maintaining heap data structures · Padding for alignment purposes · Explicit policy decisions (e.g., to return a big block to satisfy a small request) · Depends only on the pattern of previous requests · Thus, easy to measure

Internal Fragmentation Effect — Purple line: additional heap size due to allocator's data + padding for alignment · For this benchmark, 1.5% overhead · Cannot achieve in practice · Especially since cannot move allocated blocks

典型的测试曲线: 40000 个块, 开始几乎全是分配, 后来逐渐变成全是释放; 分配器必须始终高效地管理空间 (实际的分配器还能缩小堆).

内存利用率差的原因是碎片, 分两种. 内部碎片: 块比有效载荷大, 多出来的部分浪费了. 来源: 分配器自己的数据结构 (块头等)、对齐填充、策略选择 (如用大块满足小请求). 它只取决于之前的请求, 容易测量. 图中紫线 (只算内部碎片的堆大小) 比峰值只高 1.5%, 但这是假设空闲空间能完美利用, 实际做不到, 尤其是已分配的块不能移动.

外部碎片: 空闲内存的总量够, 但没有任何一个连续的空闲块够大. 例: 释放 p2 后有 40 字节空闲, 加上末尾的零星空间总量可能够 64 字节, 但不连续, malloc(64) 只能扩大堆. 它取决于将来的请求序列, 难以测量. 使用最佳适配策略时, 加上外部碎片的总开销是 8.3%.

Implementation Issues — How do we know how much memory to free given just a pointer? · How do we keep track of the free blocks? · What do we do with the extra space when allocating a structure that is smaller than the free block it is placed in? · How do we pick a block to use for allocation -- many might fit? · How do we reuse a block that has been freed?

Knowing How Much to Free — Standard method · Keep the length (in bytes) of a block in the word preceding the block. · Including the header · This word is often called the header field or header · Requires an extra word for every allocated block · (p0 = malloc(32): block size · Payload (aligned) · Padding (for alignment); free(p0))

Keeping Track of Free Blocks — Method 1: Implicit list using length—links all blocks · Need to tag each block as allocated/free · Method 2: Explicit list among the free blocks using pointers · Need space for pointers · Method 3: Segregated free list · Different free lists for different size classes · Method 4: Blocks sorted by size · Can use a balanced tree (e.g., Red-Black tree) with pointers within each free block, and the length used as a key

实现要解决五个问题: free 只给一个指针, 怎么知道释放多大? 怎么记录空闲块? 块比请求大时多余的部分怎么办? 多个空闲块都放得下时选哪个? 释放的块怎么再利用?

第一个问题的标准解法: 在块前面放一个字, 叫块头 (header), 记录整个块的长度 (包括块头本身). free(p) 时往前看一个字就知道大小. 代价是每个已分配块多一个字.

记录空闲块的四种方法: ① 隐式空闲链表, 靠块头里的长度把所有块串起来, 每块要标记已分配或空闲; ② 显式空闲链表, 在空闲块里放指针, 只串空闲块; ③ 分离空闲链表, 不同大小类别各一条链表; ④ 按大小排序的平衡树 (如红黑树). 本讲讲 ①, 下一讲讲 ②③.

Slide 25–26

Method 1: Implicit Free List — For each block we need both size and allocation status · Could store this information in two words: wasteful! · Standard trick · When blocks are aligned, some low-order address bits are always 0 · Instead of storing an always-0 bit, use it as an allocated/free flag · When reading the Size word, must mask out this bit

Format of allocated and free blocks: 1 word header “Size | a” (a = 1: Allocated block, a = 0: Free block; Size: total block size) · Payload: application data (allocated blocks only) · Optional padding

Detailed Implicit Free List Example

Double-word aligned · Allocated blocks: shaded · Free blocks: unshaded · Headers: labeled with “size in words/allocated bit” · Headers are at non-aligned positions → Payloads are aligned

每个块需要记录大小和是否已分配. 用两个字太浪费. 技巧: 块大小总是 16 的倍数, 最低 4 位总是 0, 就把最低位当作已分配标志 a. 读大小时要把低位屏蔽掉.

例子: 堆的开头留一个未用的字, 使块头位于「非对齐」位置 (地址 ≡ 8 mod 16), 这样紧跟在块头后的有效载荷正好 16 字节对齐. 块依次是 16 字节空闲、32 字节已分配、64 字节空闲、32 字节已分配, 最后是一个大小为 8、标记为已分配的结束块, 遍历到它就停. 从任一块头加上块大小就到下一个块头, 所以块串成一个「隐式」的链表.

幻灯片错误: 图注说块头标的是 "size in words/allocated bit", 但图中 16/0 的块只占 2 个字、结束块 8/1 只占 1 个字, 可见数字是字节数而不是字数 (16 字节 = 2 字, 8 字节 = 1 字). 后面的代码 (get_size、find_next) 也都按字节处理.

Implicit List: Data Structures

typedef uint64_t word_t;

typedef struct block
{
    word_t header;
    unsigned char payload[0];   // Zero length array
} block_t;

Getting payload from block pointer: return (void *) (block->payload); // block_t *block

Getting header from payload: return (block_t *) ((unsigned char *) bp - offsetof(block_t, payload)); // bp points to a payload · C function offsetof(struct, member) returns offset of member within struct

Implicit List: Header access — Getting allocated bit from header: return header & 0x1; · Getting size from header: return header & ~0xfL; · Initializing header: block->header = size | alloc; // block_t *block

Implicit List: Traversing list — Find next block

static block_t *find_next(block_t *block)
{
    return (block_t *) ((unsigned char *) block
                        + get_size(block));
}

用 C 描述块: 结构体里一个 8 字节的 header, 后面是长度为 0 的数组 payload (GNU C 扩展; C99 写法是柔性数组 payload[]), 它不占空间, 只是给「块头之后的位置」起个名字. 块指针转载荷指针: 取 block->payload; 反过来, 载荷指针减去 payload 在结构体中的偏移 (offsetof, 这里是 8) 得到块指针.

块头操作: 已分配位 = header & 1; 大小 = header & ~0xf (屏蔽低 4 位); 写块头 = size | alloc. 找下一个块: 块地址加上块大小. 注意先转成 unsigned char * 再加, 这样加的是字节数; 如果直接对 block_t * 做加法, 会按结构体大小放大.

Slide 30–31

Implicit List: Finding a Free Block

  • First fit: · Search list from beginning, choose first free block that fits: · Finding space for asize bytes (including header):
static block_t *find_fit(size_t asize)
{
    block_t *block;
    for (block = heap_start; block != heap_end;
         block = find_next(block)) {
        if (!(get_alloc(block))
            && (asize <= get_size(block)))
            return block;
    }
    return NULL;   // No fit found
}
  • Can take linear time in total number of blocks (allocated and free) · In practice it can cause “splinters” at beginning of list
  • Next fit: · Like first fit, but search list starting where previous search finished · Should often be faster than first fit: avoids re-scanning unhelpful blocks · Some research suggests that fragmentation is worse
  • Best fit: · Search the list, choose the best free block: fits, with fewest bytes left over · Keeps fragments small—usually improves memory utilization · Will typically run slower than first fit · Still a greedy algorithm. No guarantee of optimality

放置策略 (多个空闲块都够大时选哪个):

  • 首次适配 (first fit): 从头找第一个够大的空闲块. 时间与块总数 (含已分配块) 成线性; 实践中容易在链表开头留下很多小「碎屑».
  • 下次适配 (next fit): 从上次结束的地方继续找, 避免反复扫描开头那些没用的小块, 通常更快, 但有研究表明碎片更多.
  • 最佳适配 (best fit): 扫描全部, 选放下后剩余最少的块. 碎片小, 利用率通常更好, 但更慢; 而且仍是贪心算法, 不保证全局最优.

asize 是调整后的大小 (加上块头并按对齐取整), 见后面的 mm_malloc.

释放最简单的做法是把已分配位清零. 但这会产生假碎片: 两个相邻的空闲块各自都不够大, 合起来够, 分配器却看不出来. 解决: 合并 (coalesce), 释放时检查相邻块, 空闲就合成一个大块. 与后一块合并容易: 用块头的大小就能找到后一块, 看它的已分配位. 与前一块合并难: 不知道前一块从哪里开始, 也不知道它是否空闲.

Implicit List: Bidirectional Coalescing — Boundary tags [Knuth73] · Replicate size/allocated word at “bottom” (end) of free blocks · Allows us to traverse the “list” backwards, but requires extra space · Important and general technique!

边界标记 (Knuth 1973): 在块的末尾再复制一份块头, 叫块尾 (footer). 当前块的前一个字就是前一块的块尾, 读它就知道前一块的大小和是否空闲, 从而能向前遍历和合并. 代价是多占空间. 这是一个重要而通用的技术.

static word_t *header_to_footer(block_t *block)

Constant Time Coalescing — Block being freed with neighbors: Case 1: Allocated / Allocated · Case 2: Allocated / Free · Case 3: Free / Allocated · Case 4: Free / Free (previous / next)

Case 1: [m1 1][n 1][m2 1] → [m1 1][n 0][m2 1] · Case 2: [n 1][m2 0] → [n+m2 0] · Case 3: [m1 0][n 1] → [n+m1 0] · Case 4: [m1 0][n 1][m2 0] → [n+m1+m2 0]

有了边界标记, 合并只需常数时间. 释放大小为 n 的块时看前后两个邻居:

  1. 前后都已分配: 只把本块标为空闲.
  2. 后一块空闲: 与后一块合并, 新块大小 n + m2, 改本块块头和后一块块尾.
  3. 前一块空闲: 与前一块合并, 大小 n + m1, 改前一块块头和本块块尾.
  4. 前后都空闲: 三块合一, 大小 n + m1 + m2, 改前一块块头和后一块块尾.

中间被合并掉的块头块尾不用清除, 它们已在新块内部, 成了无关数据.

Heap Structure — Dummy Footer · Dummy Header · Start of heap: 8/1 16/0 32/1 64/0 32/1 8/1 · heap_start · heap_end · Dummy footer before first header · Marked as allocated · Prevents accidental coalescing when freeing first block · Dummy header after last footer · Prevents accidental coalescing when freeing final block

Top-Level Malloc Code

const size_t dsize = 2*sizeof(word_t);

void *mm_malloc(size_t size)
{
    size_t asize = round_up(size + dsize, dsize);

    block_t *block = find_fit(asize);

    if (block == NULL)
        return NULL;

    size_t block_size = get_size(block);
    write_header(block, block_size, true);
    write_footer(block, block_size, true);

    split_block(block, asize);

    return header_to_payload(block);
}

round_up(n, m) = m *((n+m-1)/m)

Top-Level Free Code

void mm_free(void *bp)
{
    block_t *block = payload_to_header(bp);
    size_t size = get_size(block);

    write_header(block, size, false);
    write_footer(block, size, false);

    coalesce_block(block);
}

堆的两端各放一个「哑」标记: 开头一个标为已分配的哑块尾, 结尾一个标为已分配的哑块头 (即前面的结束块). 这样释放第一块或最后一块时, 合并代码看到的「邻居」都是已分配的, 不会越界合并, 也不必写特殊情况.

顶层代码: mm_malloc 先把请求大小加上块头块尾 (dsize = 16 字节) 再向上取整到 16 的倍数 (round_up(n, m) = m · ⌈n / m⌉), 例如 malloc(1) 得到 32 字节的块 (课件里 asize 至少还要不小于最小块大小); 找空闲块, 找不到返回 NULL (真正的实现会用 sbrk 扩展堆再试); 标为已分配并分割; 返回载荷指针. mm_free 把块标为空闲 (块头块尾都改), 再与邻居合并.

No Boundary Tag for Allocated Blocks — Boundary tag needed only for free blocks · When sizes are multiples of 16, have 4 spare bits

a = 1: Allocated block · a = 0: Free block · b = 1: Previous block is allocated · b = 0: Previous block is free · Size: block size · Payload: application data

边界标记的缺点: 每个块多一个字, 小块的内部碎片明显. 优化: 只有空闲块需要块尾, 因为只有在前一块空闲时才需要读它的块尾. 那怎么知道前一块是否空闲? 利用块头低 4 位中的另一位 b 记录「前一块是否已分配». 于是已分配块省掉块尾, 可以多装 8 字节载荷.

Header: Use 2 bits (address bits always zero due to alignment): (previous block allocated)<<1 | (current block allocated)

(Case 1) previous m1 ?1 · block being freed n 11 → n 10 (footer n 10) · next m2 11 → m2 01 · (Case 2) n 11 · m2 10 … m2 10 → n+m2 10 … n+m2 10 · (Case 3) m1 ?0 … m1 ?0 · n 01 · m2 11 → n+m1 ?0 … n+m1 ?0 · m2 01 · (Case 4) m1 ?0 · n · m2 10 → n+m1+m2 ?0 … n+m1+m2 ?0

块头的低 2 位 = (前一块已分配) << 1 | (本块已分配). 四种合并情况都要额外维护 b 位: 释放一块后, 它变成空闲, 所以要把后一块块头的 b 位清零 (情况 1、3 中 m2 从 11 变 01). 合并后的新空闲块, 其 b 位沿用原来最前面那块的 b 位 (图中的 ?). 读者可以自己验证每一格的位都与「本块是否已分配、前一块是否已分配」一致.

Summary of Key Allocator Policies — Placement policy: · First-fit, next-fit, best-fit, etc. · Trades off lower throughput for less fragmentation · Interesting observation: segregated free lists (next lecture) approximate a best fit placement policy without having to search entire free list · Splitting policy: · When do we go ahead and split free blocks? · How much internal fragmentation are we willing to tolerate? · Coalescing policy: · Immediate coalescing: coalesce each time free is called · Deferred coalescing: try to improve performance of free by deferring coalescing until needed.

Implicit Lists: Summary — Implementation: very simple · Allocate cost: · linear time worst case · Free cost: · constant time worst case · even with coalescing · Memory Overhead · will depend on placement policy · First-fit, next-fit or best-fit · Not used in practice for malloc/free because of linear-time allocation · used in many special purpose applications · However, the concepts of splitting and boundary tag coalescing are general to all allocators

分配器的三类关键策略: 放置 (首次、下次、最佳适配; 用吞吐量换碎片; 下一讲的分离空闲链表能在不搜索整个链表的情况下近似最佳适配); 分割 (何时分割, 容忍多少内部碎片); 合并 (立即合并, 或推迟到需要时再合并以加快 free).

隐式链表小结: 实现很简单; 分配最坏线性时间 (要扫描所有块); 释放常数时间 (含合并); 内存开销取决于放置策略. 因为分配是线性时间, 通用的 malloc 不用它, 但分割和边界标记合并的思想适用于所有分配器.
