链接做什么
Linking: Motivation and What it does

Slide 2–5

Disclaimer — Linkers continue to improve their functionality to help avoid programmer mistakes · This lecture follows the textbook, although some examples may be out of date with linker defaults / terminology

Example C Program

/* main.c */
int sum(int *a, int n);

int array[2] = {1, 2};

int main(int argc, char** argv)
{
    int val = sum(array, 2);
    return val;
}

/* sum.c */
int sum(int *a, int n)
{
    int i, s = 0;
    for (i = 0; i < n; i++) {
        s += a[i];
    }
    return s;
}

Linking — Programs are translated and linked using a compiler driver: linux> gcc -Og -o prog main.c sum.c · linux> ./prog

main.c, sum.c (Source files) → Translators (cpp, cc1, as) → main.o, sum.o (Separately compiled relocatable object files) → Linker (ld) → prog (Fully linked executable object file, contains code and data for all functions defined in main.c and sum.c)

本讲讲链接: 把分别编译的多个目标文件合并成一个可执行文件. 讲师先声明: 链接器在不断改进以帮程序员避免错误, 本讲按教材讲, 有些例子可能和当前链接器的默认行为或术语不完全一致.

例子: main.c 调用 sum.c 中定义的 sum. 编译驱动程序 gcc 对每个源文件分别调用预处理器 cpp、编译器 cc1、汇编器 as, 得到可重定位目标文件 main.o、sum.o; 再调用链接器 ld 把它们合成可执行文件 prog.

Slide 6–7

Why Linkers?

  • Reason 1: Modularity
    • Program can be written as a collection of smaller source files, rather than one monolithic mass.
    • Can build libraries of common functions · e.g., Math library, standard C library
    • Header files in C declare types that are defined in libraries
  • Reason 2: Efficiency
    • Time: Separate compilation · Change one source file, compile, and then relink. · No need to recompile other source files. · Can compile multiple files concurrently.
    • Space: Libraries · Common functions can be aggregated into a single file... · Option 1: Static Linking – Executable files and running memory images contain only the library code they actually use · Option 2: Dynamic linking – Executable files contain no library code – During execution, single copy of library code can be shared across all executing processes

为什么需要链接器: ① 模块化: 程序可以拆成许多小源文件, 常用函数可以做成库 (数学库、C 标准库), 头文件声明库中定义的类型和函数. ② 效率: 时间上, 分别编译, 改一个文件只需重编这个文件再重新链接, 多个文件还能并行编译; 空间上, 用库: 静态链接时可执行文件只包含实际用到的库代码; 动态链接时可执行文件里不含库代码, 运行时所有进程共享内存中的同一份库.

Slide 8–10

What Do Linkers Do?

  • Step 1: Symbol resolution
    • Programs define and reference symbols (global variables and functions):
      • void swap() {…} /* define symbol swap */
      • swap(); /* reference symbol swap */
      • int *xp = &x; /* define symbol xp, reference x */
    • Symbol definitions are stored in object file (by assembler) in symbol table. · Symbol table is an array of entries · Each entry includes name, size, and location of symbol.
    • During symbol resolution step, the linker associates each symbol reference with exactly one symbol definition.
  • Step 2: Relocation
    • Merges separate code and data sections into single sections
    • Relocates symbols from their relative locations in the .o files to their final absolute memory locations in the executable.
    • Updates all references to these symbols to reflect their new positions.

链接器做两件事:

  1. symbol resolution 符号解析: 程序中的全局变量和函数都是符号, 有的地方定义它、有的地方引用它. 汇编器把每个目标文件定义的符号记在符号表里 (名字、大小、位置). 链接器为每个符号引用找到唯一一个定义. 例子里 main.c 定义了 array 和 main, 引用了 sum; sum.c 定义了 sum.
  2. relocation 重定位: 把各目标文件的代码节、数据节分别合并; 把符号从在 .o 文件中的相对位置移到可执行文件中的最终绝对地址; 再修改所有引用这些符号的地方, 填入新地址.

目标文件与 ELF
Object Files and ELF

Slide 11–12

Three Kinds of Object Files (Modules)

  • Relocatable object file (.o file) · Contains code and data in a form that can be combined with other relocatable object files to form executable object file. · Each .o file is produced from exactly one source (.c) file
  • Executable object file (a.out file) · Contains code and data in a form that can be copied directly into memory and then executed.
  • Shared object file (.so file) · Special type of relocatable object file that can be loaded into memory and linked dynamically, at either load time or run-time. · Called Dynamic Link Libraries (DLLs) by Windows

Executable and Linkable Format (ELF) — Standard binary format for object files · One unified format for Relocatable object files (.o), Executable object files (a.out), Shared object files (.so) · Generic name: ELF binaries

三种目标文件: 可重定位目标文件 (.o), 每个源文件生成一个, 可以和别的 .o 合并; 可执行目标文件 (a.out, gcc 不加 -o 时的默认名), 可以直接复制进内存运行; 共享目标文件 (.so, Windows 叫 DLL), 一种特殊的可重定位文件, 可以在加载时或运行时动态链接. Linux 上三者统一用 ELF 格式 (可执行与可链接格式). macOS 用的是另一种格式 Mach-O.

Slide 13–14

ELF Object File Format

  • Elf header · Word size, byte ordering, file type (.o, exec, .so), machine type, etc.
  • Segment header table · Page size, virtual address memory segments (sections), segment sizes.
  • .text section · Code
  • .rodata section · Read only data: jump tables, string constants, ...
  • .data section · Initialized global variables
  • .bss section · Uninitialized global variables · “Block Started by Symbol” · “Better Save Space” · Has section header but occupies no space
  • .symtab section · Symbol table · Procedure and static variable names · Section names and locations
  • .rel.text section · Relocation info for .text section · Addresses of instructions that will need to be modified in the executable · Instructions for modifying
  • .rel.data section · Relocation info for .data section · Addresses of pointer data that will need to be modified in the merged executable
  • .debug section · Info for symbolic debugging (gcc -g)
  • Section header table · Offsets and sizes of each section

ELF 文件由若干节 (section) 组成:

  • ELF 头: 字长、字节序、文件类型、机器类型等. 段头表 (可执行文件才需要): 告诉加载器把哪些部分映射到内存的什么地址.
  • .text 代码; .rodata 只读数据 (跳转表、字符串常量); .data 已初始化的全局变量; .bss 未初始化的全局变量, 只记录大小, 文件中不占空间 (加载时清零), 名字来自 "Block Started by Symbol", 记成 "Better Save Space".
  • .symtab 符号表; .rel.text、.rel.data 重定位信息, 记录哪些指令或数据里的地址在链接时需要改; .debug 调试信息 (gcc -g 时才有); 节头表记录每节的偏移和大小.

符号与符号解析
Step 1: Symbol Resolution

Slide 15–16

Linker Symbols

  • Global symbols · Symbols defined by module m that can be referenced by other modules. · e.g., non-static C functions and non-static global variables.
  • External symbols · Global symbols that are referenced by module m but defined by some other module.
  • Local symbols · Symbols that are defined and referenced exclusively by module m. · e.g, C functions and global variables defined with the static attribute. · Local linker symbols are not local program variables

Step 1: Symbol Resolution — main.c: Defining a global (array, main) · Referencing a global… (sum) …that's defined here (sum.c) · Linker knows nothing of val · Linker knows nothing of i or s

链接器眼中的三类符号 (以模块 m 为视角): 全局符号, m 定义、别的模块可以引用 (非 static 的函数和全局变量); 外部符号, m 引用、但在别的模块定义; 局部符号, 只在 m 内定义和使用 (加了 static 的函数和全局变量). 注意: 链接器的「局部符号」不是函数里的局部变量. 局部变量 (val、i、s) 在栈上或寄存器里, 链接器完全不知道它们.

Symbol Identification — Which of the following names will be in the symbol table of symbols.o?

/* symbols.c */
int incr = 1;
static int foo(int a) {
  int b = a + incr;
  return b;
}

int main(int argc,
         char* argv[]) {
  printf("%d\n", foo(5));
  return 0;
}

Names: incr · foo · a · argc · argv · b · main · printf · "%d\n" · Others? — Can find this with readelf: linux> readelf –s symbols.o

答案: 在符号表里的是 incr (全局变量, .data)、foo (局部符号, 因为 static)、main (全局函数)、printf (未定义的外部符号, 留给链接时解析); 另外还有文件名 symbols.c 和各节的节符号. 不在的是 a、argc、argv、b, 它们是参数和局部变量, 在寄存器或栈上. 字符串常量 "%d\n" 放在 .rodata 里, 编译器给它的临时标号 (如 .LC0) 一般不进入最终的符号表. 用 readelf -s 可以查看.

Slide 18

Local Symbols — Local non-static C variables vs. local static C variables · Local non-static C variables: stored on the stack · Local static C variables: stored in either .bss or .data

static int x = 15;

int f() {
    static int x = 17;
    return x++;
}

int g() {
    static int x = 19;
    return x += 14;
}

int h() {
    return x += 27;
}

Compiler allocates space in .data for each definition of x · Creates local symbols in the symbol table with unique names, e.g., x, x.1721 and x.1724.

函数里的普通局部变量在栈上; 而 static 局部变量和全局变量一样存在 .data (有初值) 或 .bss (无初值), 只是作用域限于函数内, 值在多次调用之间保留. 例子中有三个都叫 x 的 static 变量 (文件级、f 里、g 里), 编译器给它们分别分配空间, 并在符号表里起不同的名字 (x、x.1721、x.1724) 以区分. h 用的是文件级的 x.

Slide 19–20

How Linker Resolves Duplicate Symbol Definitions — Program symbols are either strong or weak · Strong: procedures and initialized globals · Weak: uninitialized globals · Or ones declared with specifier extern

/* p1.c */                 /* p2.c */
int foo=5;   /* strong */    int foo;    /* weak */
p1() {       /* strong */    p2() {      /* strong */
}                            }

Linker's Symbol Rules

  • Rule 1: Multiple strong symbols are not allowed · Each item can be defined only once · Otherwise: Linker error
  • Rule 2: Given a strong symbol and multiple weak symbols, choose the strong symbol · References to the weak symbol resolve to the strong symbol
  • Rule 3: If there are multiple weak symbols, pick an arbitrary one · Can override this with gcc –fno-common

同名的全局符号出现在多个模块时怎么办? 符号分强和弱: 函数和有初值的全局变量是强符号; 没有初值的全局变量 (和 extern 声明) 是弱符号. 规则: ① 不允许多个同名强符号, 否则链接错误; ② 一个强符号加若干弱符号, 选强的, 弱符号的引用都指向它; ③ 只有多个弱符号时任选一个.

补充: 从 GCC 10 起默认就是 -fno-common, 未初始化的全局变量不再按「弱符号可合并」处理, 两个文件都写 int x; 会直接报重复定义. 这正是讲师开头说「链接器在改进, 有些例子可能过时」的一例.

Important: Linker does not do type checking.

逐个理解: ① 两个 p1 都是强符号, 报错. ② 两个弱的 int x 被合成同一个变量, 两个模块无意中共享了它. ③ 两个弱 x, 链接器可能选 int 的那个 (4 字节), 而 p2 以为 x 是 8 字节的 double, 写 x 会顺带改掉紧挨着的 y. ④ 强符号 int x = 7 胜出, p2 中写 double x 同样会覆盖 y. ⑤ 弱 x 指向强 x, 共享同一个已初始化变量. 根源: 链接器只看名字, 不做类型检查.

Use of extern in .h Files (#1)

/* global.h */
extern int g;

/* c1.c */
#include "global.h"

    return g+1;
}

/* c2.c */
#include <stdio.h>

类型不匹配的后果: main 里 x 是 long (弱), 另一个文件定义 double x = 3.14 (强), 链接成功, 无任何警告. 打印的是 3.14 的 64 位位模式按 long 解释的值: 0x40091EB851EB851F = 4614253070214989087 (用 Python 核对过).

使用全局变量的建议: 能不用就不用; 要用就尽量加 static (限于本文件); 定义时一定初始化 (变成强符号, 重名会报错而不是悄悄合并); 引用别的文件的全局变量时用 extern 声明, 一般写在头文件里, 由一个 .c 文件提供唯一的定义. extern 声明本身不分配空间, 若没有任何文件定义它, 链接时报错.

幻灯片笔误: c2.c 中 int main(int argc, char argv[]) 应为 char *argv[] (或 char **argv). 另外 #include "global.h” 的结尾引号是弯引号, 照抄会编译失败.

Step 2: Relocation

重定位第一步是合并: 所有输入文件 (包括 C 运行时启动代码等「系统代码」) 的 .text 节拼成一个 .text, .data 节拼成一个 .data, 每个函数和变量由此得到最终地址. 第二步是按重定位条目修改引用.

  4004f7: 03 04 8f         add    (%rdi,%rcx,4),%eax

callq instruction uses PC-relative addressing for sum(): 0x4004e8 = 0x4004e3 + 0x5

在 main.o 里, 汇编器不知道 array 和 sum 的最终地址, 先填 0, 并记下两条重定位条目: 偏移 0xa 处的 4 字节要填 array 的绝对地址 (R_X86_64_32); 偏移 0xf 处的 4 字节要填 sum 相对于 PC 的偏移 (R_X86_64_PC32, 减 4 是因为 PC 指向这 4 字节之后的下一条指令).

链接后: array 被放到 0x601018, 小端填入 18 10 60 00; call 的操作数填 0x5, 因为 call 执行时 PC 已是下一条指令 0x4004e3, 0x4004e3 + 5 = 0x4004e8 正是 sum 的地址. PC 相对寻址使代码移动后仍然正确.

Slide 29

Loading Executable Object Files

loading 加载: 运行程序时, 加载器根据段头表把可执行文件的部分内容映射进内存: 只读代码段 (.init、.text、.rodata) 从 0x400000 开始; 读写数据段 (.data、.bss, bss 部分清零); 然后是运行时才建立的堆 (向上长, 顶端叫 brk)、共享库的映射区、用户栈. 最高处是内核的虚拟内存, 用户代码看不到. .symtab、.debug 等节不加载. 这与上一讲的内存布局一致.

静态库
Static Libraries

Slide 31–32

Packaging Commonly Used Functions — How to package functions commonly used by programmers? Math, I/O, memory management, string manipulation, etc. · Awkward, given the linker framework so far: Option 1: Put all functions into a single source file · Programmers link big object file into their programs · Space and time inefficient · Option 2: Put each function in a separate source file · Programmers explicitly link appropriate binaries into their programs · More efficient, but burdensome on the programmer

Old-fashioned Solution: Static Libraries — Static libraries (.a archive files) · Concatenate related relocatable object files into a single file with an index (called an archive). · Enhance linker so that it tries to resolve unresolved external references by looking for the symbols in one or more archives. · If an archive member file resolves reference, link it into the executable.

常用函数怎么打包? 全放一个大目标文件, 每个程序都带上全部代码, 空间和时间都浪费; 每个函数一个文件让程序员自己挑, 又太麻烦. 折中是静态库 (.a, archive): 把相关的 .o 文件连同一个索引打包成一个文件. 链接器扩展为: 遇到未解决的外部引用时到库里查找, 只把能解决引用的那些成员 .o 链接进可执行文件.

Slide 33–34

Creating Static Libraries — atoi.c printf.c random.c → Translator → atoi.o printf.o random.o → Archiver (ar): unix> ar rs libc.a atoi.o printf.o … random.o → libc.a (C standard library) · Archiver allows incremental updates · Recompile function that changes and replace .o file in archive.

Commonly Used Libraries — libc.a (the C standard library) · 4.6 MB archive of 1496 object files. · I/O, memory allocation, signal handling, string handling, data and time, random numbers, integer math · libm.a (the C math library) · 2 MB archive of 444 object files. · floating point math (sin, cos, tan, log, exp, sqrt, …)

静态库用归档工具 ar 创建 (ar rs libc.a atoi.o printf.o …). 归档支持增量更新: 改了某个函数, 只需重编译它并替换库中对应的 .o. libc.a 有约 1500 个目标文件, libm.a 有 444 个. 原文 "data and time" 应为 "date and time".

Slide 35–36

Linking with Static Libraries

/* main2.c */
#include <stdio.h>
#include "vector.h"

int x[2] = {1, 2};
int y[2] = {3, 4};
int z[2];

int main(int argc, char** argv)
{
    addvec(x, y, z, 2);
    printf("z = [%d %d]\n", z[0], z[1]);
    return 0;
}

/* addvec.c */
void addvec(int *x, int *y,
            int *z, int n) {
    int i;
    for (i = 0; i < n; i++)
        z[i] = x[i] + y[i];
}

/* multvec.c */
void multvec(int *x, int *y,
             int *z, int n)
{
    int i;
    for (i = 0; i < n; i++)
        z[i] = x[i] * y[i];
}

addvec.o multvec.o → Archiver (ar) → libvector.a · main2.c vector.h → Translators → main2.o · Linker (ld) with libvector.a (addvec.o) and libc.a (printf.o and any other modules called by printf.o) → prog2c (Fully linked executable object file, “c” for “compile-time”)

例子: addvec 和 multvec 打包成 libvector.a. main2 只调用了 addvec, 所以链接器只把 libvector.a 中的 addvec.o 拷进 prog2c, multvec.o 不会被拷入; 同样从 libc.a 中只取 printf.o 以及 printf 进一步需要的模块. 生成的 prog2c 在编译时就链接完毕.

Slide 37

Using Static Libraries — Linker's algorithm for resolving external references: · Scan .o files and .a files in the command line order. · During the scan, keep a list of the current unresolved references. · As each new .o or .a file, obj, is encountered, try to resolve each unresolved reference in the list against the symbols defined in obj. · If any entries in the unresolved list at end of scan, then error.

Problem: · Command line order matters! · Moral: put libraries at the end of the command line.

unix> gcc -L. libtest.o -lmine
unix> gcc -L. -lmine libtest.o
libtest.o: In function 'main':
libtest.o(.text+0x4): undefined reference to 'libfun'

链接器按命令行顺序只扫描一遍: 维护一个「尚未解决的引用」列表; 遇到 .o 就全部收入; 遇到 .a 时只取能解决当前列表中引用的成员; 扫描结束列表非空就报错. 所以顺序很重要: 把库放在前面时, 扫描到库时还没有任何未解决的引用 (libtest.o 还没出现), 库里的东西一个也不会被取出, 之后 libtest.o 引用 libfun 就找不到了. 规则: 库放在命令行最后; 库之间相互依赖时可能要重复写.

共享库与动态链接
Shared Libraries

Slide 38–39

Modern Solution: Shared Libraries — Static libraries have the following disadvantages: · Duplication in the stored executables (every function needs libc) · Duplication in the running executables · Minor bug fixes of system libraries require each application to explicitly relink · Rebuild everything with glibc? (https://security.googleblog.com/2016/02/cve-2015-7547-glibc-getaddrinfo-stack.html) · Modern solution: Shared Libraries · Object files that contain code and data that are loaded and linked into an application dynamically, at either load-time or run-time · Also called: dynamic link libraries, DLLs, .so files

Shared Libraries (cont.) — Dynamic linking can occur when executable is first loaded and run (load-time linking). · Common case for Linux, handled automatically by the dynamic linker (ld-linux.so). · Standard C library (libc.so) usually dynamically linked. · Dynamic linking can also occur after program has begun (run-time linking). · In Linux, this is done by calls to the dlopen() interface. · Distributing software. · High-performance web servers. · Runtime library interpositioning. · Shared library routines can be shared by multiple processes. · More on this when we learn about virtual memory

静态库的缺点: 每个可执行文件都带一份库代码 (几乎都需要 libc), 磁盘上重复; 运行时每个进程内存里也各有一份, 重复; 系统库修一个小 bug, 所有程序都要重新链接. 例子是 2015 年 glibc getaddrinfo 的栈溢出漏洞 (CVE-2015-7547): 若都是静态链接, 修补就意味着重建所有程序.

现代做法是共享库 (.so, DLL): 在加载时或运行时才动态链接. ① 加载时链接: 程序启动时由动态链接器 ld-linux.so 自动完成, libc.so 通常这样链接. ② 运行时链接: 程序运行中调用 dlopen 加载, 用于发布软件更新、高性能 Web 服务器、库打桩等. 多个进程可以共享内存中的同一份库代码 (虚拟内存那两讲再说).

What dynamic libraries are required? — .interp section · Specifies the dynamic linker to use (i.e., ld-linux.so) · .dynamic section · Specifies the names, etc of the dynamic libraries to use · Follow an example of csim-ref from cachelab: (NEEDED) Shared library: [libm.so.6]

unix> ldd csim-ref

Dynamic Linking at Load-time — unix> gcc -shared -o libvector.so addvec.c multvec.c -fpic · main2.c vector.h → Translators → main2.o (Relocatable object file) → Linker (ld) (+ relocation and symbol table info of libc.so, libvector.so) → prog2l (Partially linked executable object file) → Loader (execve) → Dynamic linker (ld-linux.so) (+ code and data of libc.so, libvector.so) → Fully linked executable in memory

可执行文件中的 .interp 节指定用哪个动态链接器, .dynamic 节列出需要的共享库 (cachelab 的 csim-ref 需要 libm.so.6). ldd 显示运行时实际找到的库及其加载地址; linux-vdso.so.1 是内核直接映射给每个进程的虚拟库 (用于快速系统调用, 如 gettimeofday).

加载时链接的流程: 用 gcc -shared -fpic 把 addvec、multvec 编成位置无关的共享库 libvector.so. 链接 main2.o 时, 链接器只从 .so 中拷贝重定位和符号表信息, 不拷贝代码, 得到「部分链接」的 prog2l. 运行时 execve 加载它, 动态链接器再把 libc.so、libvector.so 的代码和数据映射进来并完成重定位.

Slide 42–44

Dynamic Linking at Run-time

#include <stdio.h>
#include <stdlib.h>
#include <dlfcn.h>

int x[2] = {1, 2};
int y[2] = {3, 4};
int z[2];

int main(int argc, char** argv)
{
    void *handle;
    void (*addvec)(int *, int *, int *, int);
    char *error;

    /* Dynamically load the shared library that contains addvec() */
    handle = dlopen("./libvector.so", RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "%s\n", dlerror());
        exit(1);
    }
    /* Get a pointer to the addvec() function we just loaded */
    addvec = dlsym(handle, "addvec");
    if ((error = dlerror()) != NULL) {
        fprintf(stderr, "%s\n", error);
        exit(1);
    }
    /* Now we can call addvec() just like any other function */
    addvec(x, y, z, 2);
    printf("z = [%d %d]\n", z[0], z[1]);

    /* Unload the shared library */
    if (dlclose(handle) < 0) {
        fprintf(stderr, "%s\n", dlerror());
        exit(1);
    }
    return 0;
}

dll.c vector.h → Translators → dll.o → Linker (ld) (+ libc.so) → prog2r → Loader (execve) → Dynamic linker (ld-linux.so) → Fully linked executable in memory · Call to dynamic linker via dlopen (libvector.so)

运行时链接: 程序编译时根本不知道 libvector.so. 运行中调用 dlopen 加载库 (RTLD_LAZY 表示函数在第一次调用时才解析), dlsym 按名字查到 addvec 的地址, 存进函数指针后就能像普通函数一样调用, 用完 dlclose 卸载. 出错时 dlerror 返回错误信息. 链接 prog2r 时只需要 libc.so; libvector.so 由程序自己在运行时通过 dlopen 请动态链接器加载. 插件系统就是这样实现的.
