Recall: Satisfying Alignment with Structures

Slide 3

Recall: Satisfying Alignment with Structures

struct S1 {
  char c;
  int i[2];
  double v;
} *p;
  • Within structure:
    • Must satisfy each element's alignment requirement
  • Overall structure placement
    • Each structure has alignment requirement K
      • K = Largest alignment of any element
      • (Here: K = 8, due to double element)
    • Initial address & structure length must be multiples of K

alignment 对齐: 大小为 K 的基本类型, 地址必须是 K 的倍数 (int 是 4 的倍数, double 是 8 的倍数), 这样硬件一次就能读到. 结构体内部每个成员都要满足各自的对齐, 所以编译器在成员之间插入填充: c 后面空 3 字节让 i 从 4 开始, i[1] 后面空 4 字节让 v 从 16 开始.

整个结构体的对齐要求 K 取成员中最大的对齐 (这里 double 是 8), 结构体的起始地址和总长度都必须是 K 的倍数. S1 共 24 字节. (结构体的基本内容在课件编号之外的上一讲讲过, 这里是复习.)

幻灯片小错: 标题页写 "6th Lecture, Sept 11, 2025", 是 2025 年秋季学期的日期, 与 2026 年春季的课程不一致 (第 3 讲也有同样问题).

Arrays of Structures

struct S2 {

  • Start address (a) is a multiple of K
  • No padding in between array elements
  • Hence: Satisfies alignment requirement for every structure element in entire array

Programmers Can Save Space

struct S4 {          struct S5 {
  char c;              int i;
  int i;               char c;
  char d;              char d;
} *p;                } *p;

S4: c, 3 bytes, i, d, 3 bytes = 12 bytes · S5: i, c, d, 2 bytes = 8 bytes · Put large data types first · Effect (largest alignment requirement K=4)

结构体数组: 因为结构体长度本身是 K 的倍数, 数组元素之间不需要额外填充, 每个元素的每个成员自动对齐. S2 的 c 后面有 7 字节外部填充, 使长度凑成 24.

访问 a[idx].j: S3 因对齐占 12 字节 (i 2 字节 + 2 填充, v 4 字节, j 2 字节 + 2 填充), j 在偏移 8. 地址 = a + 12·idx + 8: 编译器先用 lea 算 3·idx, 再用比例因子 4 得到 12·idx, 偏移 a+8 是一个常数, 由链接器填入. movzwl 读 2 字节并零扩展.

节省空间: 成员按大小从大到小排列, 填充最少. S4 (char, int, char) 要 12 字节, S5 (int, char, char) 只要 8 字节.

x86-64 Linux Memory Layout (not drawn to scale)

  • Data · Statically allocated data · e.g., global vars, static vars, string constants

一个 x86-64 Linux 进程的虚拟地址空间 (用户部分), 从高到低:

  • 栈: 顶端在 2⁴⁷ − 4096 = 0x7FFFFFFFF000 附近, 向下增长, 默认上限 8 MB, 存局部变量等. 起始位置在 128 MB 范围内随机化.
  • 共享库: 动态链接的库代码 (如 libc), 位置也随机化.
  • 堆: malloc、calloc、new 动态分配, 向上增长.
  • 数据区: 静态分配的数据, 如全局变量、static 变量、字符串常量.
  • 代码区 (text): 程序的机器指令和只读数据, 从 0x400000 开始.

用户空间只用到 47 位地址 (约 128 TB); 地址 0 附近不映射.

Slide 14–15

Such Problems are a BIG Deal

  • Generally called a “buffer overflow” · When exceeding the memory size allocated for an array
  • Why a big deal? · It's the #1 technical cause of security vulnerabilities · #1 overall cause is social engineering / user ignorance
  • Most common form · Unchecked lengths on string inputs · Particularly for bounded character arrays on the stack · sometimes referred to as stack smashing

String Library Code — Implementation of Unix function gets()

/* Get string from stdin */
char *gets(char *dest)
{
    int c = getchar();
    char *p = dest;
    while (c != EOF && c != '\n') {
        *p++ = c;
        c = getchar();
    }
    *p = '\0';
    return dest;
}
  • No way to specify limit on number of characters to read
  • Similar problems with other library functions · strcpy, strcat: Copy strings of arbitrary length · scanf, fscanf, sscanf, when given %s conversion specification

写入超出数组分配大小的内存叫 buffer overflow 缓冲区溢出. 它是安全漏洞的头号技术原因 (总的头号原因是社会工程, 即骗人). 最常见的形式是不检查字符串输入的长度, 尤其是栈上的定长字符数组, 也叫 stack smashing 栈破坏.

罪魁之一是 gets: 它一直读到换行或文件末尾, 根本无法指定缓冲区大小. strcpy、strcat (复制任意长度的串)、带 %s 的 scanf 族也有同样的问题. gets 因此已从 C11 标准中删除.

Code Injection Attacks

  • Input string contains byte representation of executable code
  • Overwrite return address A with address of buffer B
  • When Q executes ret, will jump to exploit code

How Does The Attack Code Execute? (animation: Q's ret pops B into %rip; execution continues in the exploit code inside Q's stack frame)

代码注入: 更进一步, 输入串本身包含一段机器码 (exploit code), 把返回地址改成缓冲区 B 自己的地址. Q 执行 ret 时 %rip 变成 B, CPU 开始执行攻击者注入的代码, 攻击者就能让程序做任何事 (如打开一个 shell). 这要求两点: 能预测 B 的地址; 栈上的数据能被当作代码执行. 下面的防护措施就是破坏这两点.

防护措施
Protection

Slide 29–30

What to Do About Buffer Overflow Attacks — Avoid overflow vulnerabilities · Employ system-level protections · Have compiler use “stack canaries” · Lets talk about each…

1. Avoid Overflow Vulnerabilities in Code (!)

/* Echo Line */
void echo()
{
    char buf[4];
    fgets(buf, 4, stdin);
    puts(buf);
}
  • For example, use library routines that limit string lengths
    • fgets instead of gets
    • strncpy instead of strcpy
    • Don't use scanf with %s conversion specification · Use fgets to read the string · Or use %ns where n is a suitable integer

对付缓冲区溢出有三道防线: 代码本身不留漏洞; 系统层面的保护; 编译器插入栈保护值.

第一道: 用能限制长度的库函数. fgets(buf, 4, stdin) 最多读 3 个字符再加 '\0', 不会越界; 用 strncpy 代替 strcpy; scanf 不用裸的 %s, 改用 fgets 或写明宽度 %3s.

易错: strncpy 在源串过长时不会补 '\0' 结尾, 仍需手动处理; fgets 会把换行符也读进缓冲区.

Slide 31–32

2. System-Level Protections Can Help

  • Randomized stack offsets
    • At start of program, allocate random amount of space on stack
    • Shifts stack addresses for entire program
    • Makes it difficult for hacker to predict beginning of inserted code
    • e.g., 5 executions of memory allocation code: local 0x7ffe4d3be87c · 0x7fff75a4f9fc · 0x7ffeadb7c80c · 0x7ffeaea2fdac · 0x7ffcd452017c
    • Stack repositioned each time program executes
  • Non-executable memory
    • Older x86 CPUs would execute machine code from any readable address
    • x86-64 added a way to mark regions of memory as not executable
    • Immediate crash on jumping into any such region
    • Current Linux and Windows mark the stack this way

Any attempt to execute this code will fail

第二道, 系统层面:

  • 栈随机化 (ASLR 的一部分): 程序启动时在栈上先分配一段随机大小的空间, 整个程序的栈地址随之平移. 同一程序运行 5 次, local 的地址每次都不同. 攻击者无法预测注入代码的地址 B.
  • 不可执行内存: 老的 x86 只要能读就能执行; x86-64 增加了「不可执行」(NX) 标记位. Linux 和 Windows 把栈标记为不可执行, 跳到栈上的代码会立即崩溃, 注入的代码无法运行.

第三道, stack canary 栈保护值 (金丝雀, 来自矿工用金丝雀探测毒气): 在缓冲区之后、返回地址之前放一个随机值, 函数返回前检查它是否被改动. 溢出要改到返回地址, 必然先改掉金丝雀, 于是被发现. GCC 的 -fstack-protector 实现, 现在默认开启.

反汇编: 从 %fs:0x28 (线程局部存储中的一个随机值, 程序启动时生成) 取出金丝雀, 放在 8(%rsp), 即 buf 之后; 用 xor %eax, %eax 擦掉寄存器里的副本; 函数末尾取回栈上的值与原值异或, 相同 (结果为 0) 就正常返回, 否则调用 __stack_chk_fail 终止程序.

绕过防护: 面向返回编程
Bypassing Protection: Return-Oriented Programming

Slide 38

Return-Oriented Programming Attacks

  • Challenge (for hackers) · Stack randomization makes it hard to predict buffer location · Marking stack non-executable makes it hard to insert binary code
  • Alternative Strategy · Use existing code · Part of the program or the C library · String together fragments to achieve overall desired outcome · Does not overcome stack canaries
  • Construct program from gadgets · Sequence of instructions ending in ret · Encoded by single byte 0xc3 · Code positions fixed from run to run · Code is executable

攻击者的应对: 栈随机化让缓冲区地址难以预测, 栈不可执行让注入代码无法运行. 那就不注入代码, 而是利用程序里已有的代码: 把程序或 C 库中的小片段串起来, 实现想要的效果. 这就是 ROP (return-oriented programming, 面向返回编程). 它绕得过随机化和不可执行, 但绕不过栈保护值.

片段叫 gadget: 一小串以 ret (机器码 0xc3) 结尾的指令. 程序代码区的位置每次运行都一样 (未开启 PIE 时), 而且本来就是可执行的.

Gadget Example #1

long ab_plus_c
  (long a, long b, long c)
{
  return a*b + c;
}
00000000004004d0 <ab_plus_c>:
  4004d0: 48 0f af fe     imul   %rsi,%rdi
  4004d4: 48 8d 04 17     lea    (%rdi,%rdx,1),%rax
  4004d8: c3              retq

rax ← rdi + rdx · Gadget address = 0x4004d4 · Use tail end of existing functions

Gadget Example #2

void setval(unsigned *p) {
  *p = 3347663060u;
}
<setval>:
  4004d9: c7 07 d4 48 89 c7   movl   $0xc78948d4,(%rdi)
  4004df: c3                  retq

Encodes movq %rax, %rdi · rdi ← rax · Gadget address = 0x4004dc · Repurpose byte codes

两种找 gadget 的方法. ① 利用现成函数的结尾: ab_plus_c 从 0x4004d4 开始的两条指令是 lea (%rdi,%rdx), %rax; ret, 效果 rax ← rdi + rdx. ② 重新解读字节: setval 里的常数 3347663060 = 0xc78948d4, 按小端存放的字节是 d4 48 89 c7. 从 0x4004dc (指令中间) 开始读, 字节 48 89 c7 c3 恰好是 movq %rax, %rdi; ret. x86 指令变长、没有对齐要求, 从任意字节开始都可能解出合法指令, 这让 gadget 非常多. (常数的十六进制用 Python 核对过.)

Slide 41–43

ROP Execution — Trigger with ret instruction · Will start executing Gadget 1 · Final ret in each gadget will start next one · ret: pop address from stack and jump to that address

Crafting an ROP Attack String

Gadget #1 · 0x4004d4 rax ← rdi + rdx · Gadget #2 · 0x4004dc rdi ← rax · Combination: rdi ← rdi + rdx · Multiple gadgets will corrupt stack upwards

What Happens When echo Returns? 1. Echo executes ret · Starts Gadget #1 · 2. Gadget #1 executes ret · Starts Gadget #2 · 3. Gadget #2 executes ret · Goes off somewhere ...

ROP 的执行: 在栈上依次放 gadget 地址. echo 的 ret 弹出第一个地址, 进入 gadget 1; gadget 1 末尾的 ret 再从栈上弹出下一个地址, 进入 gadget 2; 以此类推. 每个 ret 都在「执行」栈上的下一条「指令」(地址), 栈相当于程序, %rsp 相当于程序计数器.

例子: 24 字节填充 + 0x4004d4 + 0x4004dc, 组合效果 rdi ← rdi + rdx. 多个 gadget 会一直向上覆盖栈. gadget 2 返回后栈上没有安排, 程序就跑飞了 (真实攻击会继续安排后续 gadget). attacklab 的后两题就是 ROP.

Union Allocation

  • Allocate according to largest element
  • Can only use one field at a time
union U1 {             struct S1 {
  char c;                char c;
  int i[2];              int i[2];

Using Unions as Sum Types

typedef union {
  float f;
  unsigned u;
} num_t;

typedef struct {
  bool is_float;
  num_t val;
} value_t;

(technically is_float only takes 1 byte and then there's 3 bytes of padding)

用联合查看位模式: 把 unsigned 写进 u, 再从 f 读出, 得到的是「同一组 32 位按 float 解释」的值. 这不同于 (float) u: 强制类型转换会转换数值 (把 1 变成 1.0f, 位模式完全不同), 而联合保持位模式不变. 同理 float2bit 也不同于 (unsigned) f (后者会截断成整数).

作为和类型: 结构体里放一个标记 is_float 说明当前联合里存的是哪种值, 再放联合本身. 这是 C 里模拟「要么是 float、要么是 unsigned」的常用写法. is_float 只占 1 字节, 后面 3 字节填充, 使 val 从 4 开始.

Impact of x86-64 Byte Ordering on Unions

union {
  unsigned char c[8];
  unsigned short s[4];
  unsigned int i[2];
  unsigned long l[1];
} dw;

int j;
for (j = 0; j < 8; j++)
  dw.c[j] = 0xf0 + j;
Characters 0-7 == [0xf0,0xf1,0xf2,0xf3,0xf4,0xf5,0xf6,0xf7]
Shorts 0-3 == [0xf1f0,0xf3f2,0xf5f4,0xf7f6]
Ints 0-1 == [0xf3f2f1f0,0xf7f6f5f4]
Long 0 == [0xf7f6f5f4f3f2f1f0]

Byte Ordering on IA32 (Little Endian): … Long 0 == [0xf3f2f1f0] · Byte Ordering on Sun (Big Endian): Shorts 0-3 == [0xf0f1,0xf2f3,0xf4f5,0xf6f7] · Ints 0-1 == [0xf0f1f2f3,0xf4f5f6f7] · Long 0 == [0xf0f1f2f3]

联合直观展示字节序: 往 8 个字节依次写 f0…f7, 再按 short、int、long 读出. x86-64 是小端, 低地址的字节是低位, 所以第一个 short 是 0xf1f0, 第一个 int 是 0xf3f2f1f0, long 是 0xf7f6f5f4f3f2f1f0. 大端的 Sun (SPARC) 正好相反: 0xf0f1、0xf0f1f2f3. IA32 和 32 位 Sun 上 long 只有 4 字节, 所以 l[0] 只包含前 4 个字节.
