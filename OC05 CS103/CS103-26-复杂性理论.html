The Limits of Decidability

Slide 2–3

(图片: 图灵 1936 年论文 On Computable Numbers; 1945 年的 ENIAC, First General-Purpose Electronic Digital Computer.)

A Decidable Problem

  • Consider the following problem:

    Given two regular expressions R1​ and R2​, determine whether R1​ and R2​ have the same language.

  • This problem is indeed decidable.
    • We autograded your regular expressions in Problem Set Seven. The algorithm we used is 100% accurate.
  • Theorem: There is no algorithm for solving this problem whose runtime is O(2m+n), where m and n are the lengths of the input regular expressions.

课程最后一部分: 复杂性理论. 例子: 判断两个正则表达式的语言是否相同. 这个问题可判定 (作业自动评分器就在做这件事: 都转成 DFA 再比较), 但已知没有运行时间为 O(2m+n) 的算法, 也就是说它需要比指数还多的时间. 可判定不等于实际上能解决.

Slide 4

The Limits of Decidability

  • The fact that a problem is decidable does not mean that it is feasibly decidable.
  • In computability theory, we ask the question What problems can be solved by a computer?
  • In complexity theory, we ask the question What problems can be solved efficiently by a computer?
  • In the remainder of this course, we will explore this question in more detail.

可判定不代表能可行地判定. computability theory 可计算性理论问「计算机能解决什么问题」; complexity theory 复杂性理论问「计算机能高效地解决什么问题」. 课程剩下的部分研究后者.

  • The class R represents problems that can be solved by a computer.
  • The class RE represents problems where “yes” answers can be verified by a computer.

Where We're Going

  • The class P represents problems that can be solved efficiently by a computer.
  • The class NP represents problems where “yes” answers can be verified efficiently by a computer.

The Setup

  • In order to study computability, we needed to answer these questions:
    • What is “computation?”
    • What is a “problem?”
    • What does it mean to “solve” a problem?
  • To study complexity, we need to answer these questions:
    • What resources do we want our programs to make “efficient” use of?
    • How do we draw the line between “efficient” and “inefficient?”

Correctness

  • We have a program written in your Favorite Programming Language that's a decider for some problem.
  • What does it mean for this program to be correct?

Efficiency

  • We have a program written in your Favorite Programming Language that's a decider for some problem.
  • What aspect of that program might quantify “efficiency?”
    • The number of lines of code in the program.
    • How deeply-nested the loops or recursion in the program are.
    • How much time it takes for the program to solve the problem.
    • How much memory it takes for the program to solve the problem.
    • How much power it takes for the program to solve the problem.
    • How much network communication it takes for the program to solve the problem.
    • …

What is an efficient algorithm? Let's explore some problems and solutions and see what we notice!

研究可计算性要先定义「计算」「问题」「解决」; 研究复杂性还要回答: 用什么资源来衡量「高效」, 高效与低效的分界在哪里.

衡量一个判定程序的效率有很多角度: 代码行数、循环嵌套深度、运行时间、内存、耗电、网络通信量等. 课件高亮的是运行时间, 后面都以时间为准.

A Common Pattern: Searching Finite Spaces

Slide 15

A Common Pattern: Searching Finite Spaces

  • Many decidable problems can be solved by searching over a large but finite space of possible options.
  • Searching this space might take a staggeringly long time, but only finite time.
  • From a decidability perspective, this is totally fine.
  • From a complexity perspective, this may be totally unacceptable.

很多可判定问题都可以在一个巨大但有限的空间里搜索答案. 搜索可能要花惊人的时间, 但总会结束. 从可判定性看这完全没问题; 从复杂性看可能完全不可接受.

Slide 16–21

A Sample Problem

4 3 11 9 7 13 5 6 1 12 2 8 0 10

Goal: Find the length of the longest increasing subsequence of this sequence.

Longest Increasing Subsequences

  • One possible algorithm: try all subsequences, find the longest one that's increasing, and return that.
  • There are 2n subsequences of an array of length n.
    • (Each subset of the elements defines a subsequence.)
  • Checking all of them to find the longest increasing subsequence will take time O(n⋅2n).
  • Fact: the age of the universe is about 4.3×1026 nanoseconds. That's about 285 nanoseconds.
  • Practically speaking, this algorithm doesn't terminate if you give it an input of size 100 or more.

问题: 求数列的 longest increasing subsequence 最长递增子序列 (子序列可以不连续, 但要保持原顺序). 例子的答案是 5, 如 4, 5, 6, 8, 10 (用 Python 核对过).

朴素算法: 枚举全部 2n 个子序列, 逐个检查, 时间 O(n⋅2n). 宇宙年龄约 4.3×1026 纳秒; n = 100 时 2100≈1.3×1030, 远超宇宙年龄, 实际上永远算不完.

幻灯片错误: “That's about 285 nanoseconds” 不对. 285≈3.9×1025, 只有 4.3×1026 的十分之一左右; log2​(4.3×1026)≈88.5, 应为约 288–289. 宇宙年龄 138 亿年约 4.35×1026 纳秒, 这个数是对的. 结论 (n ≥ 100 时算不完) 不受影响.

Slide 22–27

A Different Approach — Patience Sorting

Place each number on top of a pile. Put each number on top of the first pile whose top value is larger than it. (If you can't, make a new pile.) Then, add a link to the top number in the previous pile.

Trace backwards from the top of the last pile. The numbers you visit form one of the longest increasing subsequences of your original sequence.

Longest Increasing Subsequences

  • Theorem: There is an algorithm that can find the longest increasing subsequence of an array in time O(n2).
    • It's the previous patience sorting algorithm, with some clever implementation tricks.
  • This algorithm works by exploiting particular aspects of how longest increasing subsequences are constructed. It's not immediately obvious that it works correctly.

另一种方法 patience sorting 耐心排序 (来自纸牌游戏): 从左到右处理, 每个数放到第一个堆顶比它大的堆上, 没有就新开一堆; 同时记一条指向前一堆当前堆顶的链接. 最后堆的个数就是最长递增子序列的长度 (这里 5 堆), 从最后一堆的顶沿链接往回走, 得到一个最长递增子序列 3, 5, 6, 8, 10.

它的时间是 O(n2) (用二分查找可做到 O(nlogn)). 关键是它利用了递增子序列的结构, 而不是盲目搜索; 正确性并不显然.

为什么堆数就是答案 (直觉): 每一堆从下到上是递减的 (新数只放在比它大的堆顶上), 所以一个递增子序列在每一堆里至多取一个数, 长度不超过堆数. 反过来, 每个数放下时指向前一堆当时的顶, 那个数在原序列中更早出现而且更小, 沿链接往回走正好得到一条长度等于堆数的递增子序列. 两方面合起来, 堆数就是最长长度. 例子里最终的五堆 (从下到上) 是 4 3 1 0、11 9 7 5 2、13 6、12 8、10.

Slide 28–33

Another Problem

Goal: Determine the length of the shortest path from F to A in this graph.

Shortest Paths

  • It is possible to find the shortest path in a graph by listing off all sequences of nodes in the graph in ascending order of length and finding the first that's a path.
  • This takes time O(n⋅n!) in an n-node graph.
  • For reference: 29! nanoseconds is longer than the lifetime of the universe.

Pop Quiz! How else could we find a shortest path?

  • Theorem: It's possible to find the shortest path between two nodes in an n-node, m-edge graph in time O(m+n).
  • Proof idea: Use breadth-first search!
  • This scales nicely!
  • The algorithm is a bit nuanced. It uses some specific properties of shortest paths and the proof of correctness is nontrivial.

第二个问题: 求图中 F 到 A 的最短路径. 例图的答案是 3: F → D → E → A.

朴素方法: 按长度从小到大枚举所有节点序列, 找到第一条合法路径, 时间 O(n⋅n!). 29! ≈ 8.8×1030 纳秒, 远超宇宙年龄. 聪明的方法: breadth-first search 广度优先搜索, 从起点一层层向外扩展, 时间 O(m+n), 规模变大也很快. 但它的正确性证明依赖最短路径的特定性质.

广度优先搜索在例图上的过程: 从 F 出发, 第 1 层是 F 的邻居 D; 第 2 层是 D 的新邻居 B、C、E; 第 3 层是 E 的新邻居 A, 找到目标, 距离 3. 每个节点只进队一次、每条边只看常数次, 所以时间是 O(n + m). 为什么第一次到达 A 时的层数就是最短距离: 层是按距离从小到大展开的, 距离为 k 的节点都在第 k 层被发现.

Slide 34–36

For Comparison

  • Longest increasing subsequence:
    • Naive: O(n⋅2n)
    • Fast: O(n2)
  • Shortest path problem:
    • Naive: O(n⋅n!)
    • Fast: O(n+m).

Defining Efficiency

  • When dealing with problems that search for the “best” object of some sort, there are often at least exponentially many possible options.
  • Brute-force solutions tend to take at least exponential time to complete.
  • Clever algorithms often run in time O(n), or O(n2), or O(n3), etc.

Polynomials and Exponentials

  • An algorithm runs in polynomial time if its runtime is some polynomial in n.
    • That is, time O(nk) for some constant k.
  • Polynomial functions “scale well.”
    • Small changes to the size of the input do not typically induce enormous changes in the overall runtime.
  • Exponential functions scale terribly.
    • Small changes to the size of the input induce huge changes in the overall runtime.

两个问题的共同规律: 寻找「最好的」对象时, 候选通常至少有指数多个, 暴力搜索至少要指数时间; 聪明的算法往往是 O(n)、O(n2)、O(n3) 这类.

polynomial time 多项式时间: 运行时间为 O(nk), k 是常数. 多项式「伸缩性好」: 输入稍大一点, 时间不会暴涨 (n 翻倍, n2 只变成 4 倍). 指数则相反: n 加 1, 2n 就翻倍.

Cobham-Edmonds 论题与 P
The Cobham-Edmonds Thesis

Slide 37–39

The Cobham-Edmonds Thesis

  • A language L can be decided efficiently if there is a TM that decides it in polynomial time.
  • Equivalently, L can be decided efficiently if it can be decided in time O(nk) for some k∈N.

Like the Church-Turing thesis, this is not a theorem! It's an assumption about the nature of efficient computation, and it is somewhat controversial.

Which of the following are considered efficient runtimes?

1n2−3n+17✓ This is a polynomial in n.
2nlogn✓ Bounded by n2.
3n1,000,000,000✓ This is a polynomial in n.
4nn✗ Eventually bigger than nk for all k.
5n!✗ Eventually bigger than nk for all k.
62n✗ Eventually bigger than nk for all k.
71.0000001n✗ Eventually bigger than nk for all k.
810500✓ 10500=10500n0 is a polynomial in n.

Cobham-Edmonds thesis 科巴姆-埃德蒙兹论题: 一个语言能被高效判定, 当且仅当有图灵机在多项式时间内判定它. 和 Church-Turing 论题一样, 它不是定理, 而是对「高效计算」的一种约定, 而且有争议.

八个运行时间里, 多项式 (1, 2, 3, 8) 算高效, 其余 (nn、n!、2n、1.0000001n) 不算: 它们最终会超过任何 nk. 争议正在这里: n109 被算作高效, 实际上完全不可用; 而 1.0000001n 在很大的 n 之前都比它快. 常数 10500 也算多项式 (零次).

为什么还要接受这个约定: 实际中出现的多项式算法, 指数通常很小 (n2、n3), 而且一旦找到多项式算法, 后来往往能继续改进; 指数算法则在问题规模稍大时就彻底失效. 另外「多项式时间」与具体机器模型无关: 图灵机、普通计算机之间的相互模拟只带来多项式倍的开销, 所以 P 在各种合理模型下都是同一个类.

Slide 40–42

Why Polynomials?

  • Polynomial time somewhat captures efficient computation, but has a few edge cases.
  • However, polynomials have very nice mathematical properties:
    • The sum of two polynomials is a polynomial. (Running one efficient algorithm, then another, gives an efficient algorithm.)
    • The product of two polynomials is a polynomial. (Running one efficient algorithm a “reasonable” number of times gives an efficient algorithm.)
    • The composition of two polynomials is a polynomial. (Using the output of one efficient algorithm as the input to another efficient algorithm gives an efficient algorithm.)

The Complexity Class P

  • The complexity class P (for polynomial time) contains all problems that can be solved in polynomial time.
  • Formally: P={L∣There is a polynomial-time decider for L}
  • Assuming the Cobham-Edmonds thesis, a language is in P if it can be decided efficiently.

Examples of Problems in P

  • All regular languages are in P.
    • All have linear-time TMs.
  • All CFLs are in P.
    • Requires a more nuanced argument (the CYK algorithm or Earley's algorithm).
  • And a ton of other problems are in P as well.
    • Curious? Take CS161!

为什么选多项式? 它只是「大致」刻画了高效, 但数学性质很好: 两个多项式的和、积、复合仍是多项式. 对应到算法: 先后运行两个高效算法、把高效算法运行「合理」多次、把一个高效算法的输出喂给另一个, 结果都还是高效的. 这让 P 在各种组合下稳定.

P: 所有有多项式时间判定器的语言. 例子: 所有正则语言 (DFA 线性时间); 所有上下文无关语言 (用 CYK 或 Earley 算法, 立方时间); 以及算法课里的大量问题.

Slide 56–58

Verifiers

  • Recall that a verifier for L is a TM V such that
    • V halts on all inputs.
    • w∈L↔∃c∈Σ∗. V accepts ⟨w,c⟩.

Polynomial-Time Verifiers

  • A polynomial-time verifier for L is a TM V such that
    • V halts on all inputs.
    • w∈L↔∃c∈Σ∗. V accepts ⟨w,c⟩.
    • V's runtime is a polynomial in ∣w∣ (that is, V's runtime is O(∣w∣k) for some integer k).

The Complexity Class NP

  • The complexity class NP (nondeterministic polynomial time) contains all problems that can be verified in polynomial time.
  • Formally: NP={L∣There is a polynomial-time verifier for L}
  • The name NP comes from another way of characterizing NP. If you introduce nondeterministic Turing machines and appropriately define “polynomial time,” then NP is the set of problems that an NTM can solve in polynomial time.
  • Useful fact: NP⊊R.
    • Proof idea: If L∈NP, all strings in L have “short” certificates. Therefore, we can just try all possible “short” certificates and see if any of them work. (Showing NP is a strict subset of R requires some more advanced techniques.)

polynomial-time verifier 多项式时间验证器: 在上一讲验证器的定义上, 再要求运行时间是 |w| 的多项式. 因为验证器只有多项式时间, 它只能读证书的多项式长度部分, 所以等价于证书「短」.

NP (nondeterministic polynomial time 非确定多项式时间): 所有有多项式时间验证器的语言. 名字来自另一种等价刻画: 非确定图灵机在多项式时间内能解决的问题 (呼应 NFA 的「猜测」: 猜一个证书, 再确定地验证).

NP 的问题都可判定: 证书短, 就把所有短证书逐个试一遍 (指数时间, 但有限). 实际上 NP 是 R 的真子集, 证明需要更高级的技巧.

易错: NP 不是「not polynomial」的缩写.

Slide 69–71

P ≟ NP

  • The P ≟ NP question is the most important open question in theoretical computer science.
  • With the verifier definition of NP, one way of phrasing this question is

    If a solution to a problem can be checked efficiently, can that problem also be solved efficiently?

  • An answer either way will give fundamental insights into the nature of computation.

Why This Matters

  • The following problems are known to be efficiently verifiable, but have no known efficient solutions:
    • Determining whether an electrical grid can be built to link up some number of houses for some price (Steiner tree problem).
    • Determining whether a simple DNA strand exists that multiple gene sequences could be a part of (shortest common supersequence).
    • Determining the best way to assign hardware resources in a compiler (optimal register allocation).
    • Determining the best way to distribute tasks to multiple workers to minimize completion time (job scheduling).
    • And many more.
  • If P = NP, all of these problems have efficient solutions.
  • If P ≠ NP, none of these problems have efficient solutions.

用验证器的语言, P ≟ NP 就是: 如果一个问题的答案能被高效检查, 它是否也能被高效解决? 无论答案是什么, 都会深刻揭示计算的本质.

实际意义: 很多重要问题能高效验证, 却没有已知的高效算法: Steiner 树 (用一定预算的电网连接若干房屋)、最短公共超序列 (DNA 拼接)、最优寄存器分配 (编译器)、作业调度. 若 P = NP, 这些问题全部有高效算法; 若 P ≠ NP, 它们全都没有. 这个「全有或全无」来自 NP 完全性 (这些问题彼此能高效转化), 是下一讲的内容.

补充 NP-complete NP 完全的含义 (下一讲正式讲): 一个 NP 问题叫 NP 完全, 如果每个 NP 问题都能在多项式时间内转化成它. 于是只要有一个 NP 完全问题有多项式算法, 所有 NP 问题就都有, P = NP; 反之只要有一个 NP 问题没有多项式算法, 所有 NP 完全问题都没有. 上面列的 Steiner 树、最短公共超序列、寄存器分配、作业调度, 以及第 9 讲的独立集、顶点覆盖和本讲的哈密顿路径, 都是 NP 完全问题 (的判定版本).

Slide 71–74

Why This Matters

  • If P = NP:
    • A huge number of seemingly difficult problems could be solved efficiently.
    • Our capacity to solve many problems will scale well with the size of the problems we want to solve.
  • If P ≠ NP:
    • Enormous computational power would be required to solve many seemingly easy tasks.
    • Our capacity to solve problems will fail to keep up with our curiosity.

What We Know

  • Resolving P ≟ NP has proven extremely difficult.
  • In the past 50 years:
    • Not a single correct proof either way has been found.
    • Many types of proofs have been shown to be insufficiently powerful to determine whether P ≟ NP.
    • A majority of computer scientists believe P ≠ NP, but this isn't an overwhelming majority.
  • Interesting read: Interviews with leading thinkers about P ≟ NP: https://www.cs.umd.edu/~gasarch/papers/poll.pdf

The Million-Dollar Question

The Clay Mathematics Institute has offered a $1,000,000 prize to anyone who proves or disproves P = NP.

“My hunch is that [P ≟ NP] will be solved by a young researcher who is not encumbered by too much conventional wisdom about how to attack the problem.” – Prof. Richard Karp (The guy who first popularized the P ≟ NP problem.)

两种结局: 若 P = NP, 大量看似困难的问题都能高效解决, 解决能力随问题规模良好伸缩; 若 P ≠ NP, 许多看似简单的任务需要巨大的计算量, 我们的计算能力跟不上好奇心.

现状: 五十年来没有任何正确的证明; 多种证明方法被证明力量不够 (见下文); 多数计算机科学家相信 P ≠ NP, 但并非压倒性多数 (Gasarch 的民意调查). 克雷数学研究所为证明或否证 P = NP 悬赏 100 万美元 (千禧年大奖难题之一). Karp (最早推广这个问题的人) 猜测它会被一位不受传统思路束缚的年轻研究者解决.

What do we know about P ≟ NP?

Adapting our Techniques

P={L∣there is a polynomial-time decider for L}
NP={L∣there is a polynomial-time verifier for L}
R={L∣there is a decider for L}
RE={L∣there is a verifier for L}

We know that R=RE. So does that mean P=NP?

A Problem

  • The R and RE languages correspond to problems that can be decided and verified, period, without any time bounds.
  • To reason about what's in R and what's in RE, we used two key techniques:
    • Universality: TMs can simulate other TMs.
    • Self-Reference: TMs can get their own source code.
  • Why can't we just do that for P and NP?

Theorem (Baker-Gill-Solovay): Any proof that purely relies on universality and self-reference cannot resolve P ≟ NP.

Proof: Take CS154!

为什么不能照搬 R ≠ RE 的证明来证 P ≠ NP? R ≠ RE 用到两个技巧: 通用性 (模拟别的机器) 和自指 (拿到自己的源代码), 即 trickster 式的对角线论证. Baker-Gill-Solovay 定理 (1975) 表明: 只依赖这两个技巧的证明 (术语叫「相对化」的证明) 无法解决 P ≟ NP. 这是上面「多种证明方法被证明力量不够」的第一个例子. 详见 CS154.
